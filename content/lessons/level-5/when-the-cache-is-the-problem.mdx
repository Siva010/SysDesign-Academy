## The problem

The cache is at a 95% hit rate and has been for a year. The database sits at 12% CPU. Everything
is comfortable.

At 09:00 on a Tuesday the cache cluster is restarted for a routine upgrade, one node at a time.
Within four seconds the database is at 100% CPU, queries are queuing, timeouts are firing, and the
application is returning errors to every user — including the 95% whose requests would have been
served from cache, because the application is now out of workers.

Nothing failed. The cache came back in ninety seconds. The database did not recover for forty
minutes, because by then every client was retrying.

The database was never sized to serve this traffic. It was sized to serve 5% of it, and that
decision was made quietly, by whoever observed that the hit rate was 95% and provisioned
accordingly.

## Intuition

Adding a cache feels like adding speed. It also does something less visible: **it changes what the
origin is sized for.**

Once the origin is provisioned against a 95% hit rate, the cache is not an optimisation. It is a
load-bearing dependency, and the interesting question stops being &ldquo;how fast is it&rdquo; and
becomes &ldquo;in how many ways can it stop absorbing traffic?&rdquo;

There are more ways than people expect, and they have one thing in common: they are **correlated**.
Ordinary traffic is many independent users doing unrelated things, and it averages out. Cache
misses are not independent. Everyone misses the same key at the same instant because it expired at
the same instant. Every instance has a cold local cache at the same moment because they were all
deployed together. Every request scans the whole cluster after a node is lost.

That is the shape of the whole subject: **a cache converts a capacity problem into a correlation
problem**, and correlated load arrives as a spike rather than as an increase.

## Concretely

<Example title="Four ways a cache stops absorbing load">

An origin sized for 5,000 requests per second behind a cache serving 100,000.

**Expiry of a hot key.** One key gets 20,000 requests per second. Its entry expires. In the
milliseconds before anything repopulates it, every one of those requests misses and goes to the
origin — a four-fold overload from one key, and no error anywhere reported until the origin fails.

**A deploy.** Every application instance restarts with an empty local cache. Local hit rate goes
from 60% to 0 across the fleet simultaneously, and the shared cache and the origin behind it both
see a step change that lasts until the caches warm.

**Keys that do not exist.** A scanner requests one million product identifiers that were never
issued. Each one misses, reaches the origin, finds nothing, and caches nothing — so the next
identical request misses again. The cache is a pure pass-through for this traffic and the origin
absorbs all of it.

**A neighbour.** Another team starts writing 5 MB objects into the shared cache. Eviction pressure
climbs, your working set no longer fits, and your hit rate falls from 95% to 70%. You have changed
nothing, and your origin load has increased six-fold.

Each of these is a hit-rate change and every one of them arrives as a step, not a slope.

</Example>

## Formal explanation

**<C id="cache-stampede" />** — also called a dog-pile — is many concurrent requests for the same
key missing at the same moment and all being forwarded. Whether it hurts depends on one ratio: the
time to recompute the value against the request rate for that key. A 200 ms computation and 20,000
requests per second means 4,000 concurrent recomputations of the identical value.

Four mitigations, and they compose:

- **<C id="request-coalescing" />.** One request per key recomputes; the rest wait for its result.
  This is the single most effective mitigation because it caps concurrent origin work at one per
  key regardless of demand. It must be applied per instance *and* ideally cluster-wide, because a
  hundred instances each coalescing to one still produce a hundred.
- **Serve stale while revalidating.** Return the expired value immediately and refresh in the
  background. Nobody waits, the origin sees one request, and the cost is bounded staleness — which
  most content can accept and some cannot.
- **Early probabilistic refresh.** As expiry approaches, each request has a small and rising
  chance of refreshing the entry. The value is refreshed slightly early by one request rather than
  simultaneously by all of them.
- **Jittered lifetimes.** Populating a thousand entries in one batch with an identical lifetime
  guarantees they expire together. Add randomness at write time and the expiry spreads.

**<C id="cache-penetration" />** is traffic for keys that do not exist. Because there is nothing to
store, the cache never populates and every request reaches the origin. It arises from a scanner, a
broken client looping over identifiers, or a deliberate attack — and it is the one failure mode
here where a caching layer provides zero protection by default.

- **Cache the negative result** with a short lifetime. This alone removes most of it. The short
  lifetime matters, because a key that is created later must become visible.
- **A <C id="bloom-filter" /> of existing keys** answers &ldquo;definitely not present&rdquo;
  cheaply, with a small false-positive rate that costs only an occasional unnecessary lookup.
- **Validate the key shape** before doing any work. Most scanning traffic requests identifiers that
  could never have been issued.

**<C id="fanout-latency-amplification" />** is what happens when one user request makes many cache
calls. If a page makes 50 lookups and each has a 1% chance of being slow, the probability that
*at least one* is slow is about 39%. The page's tail latency is governed by the slowest of the
fifty, not by the median of one (<Cite id="tail-at-scale" />).

The fixes are all about reducing the number of independent chances to be slow: batch the lookups
into one multi-key request, reduce the fanout, or set a per-call deadline with a defined fallback.
And the measurement follows from it — the number that predicts page latency is the cache's p99,
multiplied out by the fanout, and not its average, which will look excellent throughout.

**<C id="noisy-neighbour" />** is a shared cache behaving like any shared resource. Another
tenant's large values or scan-heavy access pattern evicts your working set, and your hit rate falls
without anything in your system changing. The signature is distinctive and worth recognising:
**your hit rate dropped and you deployed nothing.**

- Separate caches for workloads with genuinely different access patterns — an analytics job and a
  serving path should not share eviction pressure.
- Per-tenant memory quotas where the technology supports them.
- Value size limits, because a small number of very large values does most of the damage.

## Trade-offs

<TradeOff
  decision="Serve stale content while revalidating in the background, instead of blocking on a refresh"
  options={[
    'Block every request until the value is recomputed',
    'Coalesce misses so one request recomputes and the rest wait for it',
    'Serve the stale value immediately and refresh in the background',
    'Refresh proactively before expiry, on a schedule',
  ]}
  why="The moment a hot value expires is the moment demand for it is highest. Blocking converts one expiry into thousands of simultaneous waits and one enormous burst of origin work, for a value that was correct a second ago."
  gain="No user waits for a recomputation. The origin sees one request per key per refresh regardless of demand. Latency stays flat across expiry rather than spiking at it, and the cache stops being a source of correlated load."
  sacrifice="Users receive data known to be expired. Staleness is now unbounded if the refresh keeps failing — the stale value can be served indefinitely while the origin is broken, which hides the failure."
  failureModes={[
    'Stale data served long past any acceptable window because refreshes are failing silently',
    'A refresh loop that never succeeds, so nobody ever sees a fresh value and nothing alerts',
    'Serving stale for data where staleness is a correctness problem rather than a quality one',
  ]}
  operationalBurden="Low to implement, and it needs two pieces of instrumentation that are easy to omit: the age of served values, and the success rate of background refreshes. Without those, the mechanism fails silently by design."
  cost="A little extra memory for entries kept past expiry, and background refresh traffic that runs whether or not anyone asked."
  whenNot="When staleness is a correctness problem: a permission that was revoked, a price at the point of sale, a balance before a transfer. There, blocking on a fresh read is correct and coalescing is the right mitigation instead. Also cap how long stale may be served — a bounded window, after which requests block or fail — or a broken origin becomes an invisible outage in which everyone is confidently served last week's answers."
/>

## In production

<RealWorld>

<Claim label="convention" source="aws-builders-library">
Correlated retries and simultaneous refreshes are described as a primary source of overload,
because clients that failed or expired together return together. Randomisation and limiting
concurrent work per key are the standard mitigations.
</Claim>

<Claim label="fact" source="redis-docs">
Keys can be given expiry times, and eviction policies decide what is removed when memory is
exhausted. A shared instance therefore evicts across all workloads sharing it, according to one
policy configured for the instance rather than per client.
</Claim>

<Claim label="fact" source="tail-at-scale">
When a single request depends on many servers, the probability that at least one responds slowly
rises quickly with fanout, so overall latency is governed by the slowest component rather than the
typical one.
</Claim>

<Claim label="recommendation" source="sre-book">
Systems should be tested against the failure of their dependencies rather than assumed to degrade
gracefully. A cache whose loss has never been exercised is an untested dependency in the critical
path.
</Claim>

<Claim label="convention" source="release-it">
Failures propagate through shared resources: a component that consumes a shared pool, cache or
thread supply degrades every other consumer of it, which is why isolation between workloads is a
stability pattern rather than an efficiency one.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Treating the cache as an optimisation once the origin is sized around it.',
      why: 'At a 95% hit rate the origin is provisioned for a twentieth of the traffic. The cache is now in the critical path, and its failure is a total outage rather than a slowdown, whatever the diagram suggests.',
      instead:
        'State the origin capacity as a multiple of full traffic, and have an explicit plan for a zero percent hit rate: shed, degrade, or provision. Then test it deliberately.',
    },
    {
      mistake: 'Monitoring cache availability instead of hit rate.',
      why: 'The cache can be perfectly available and absorbing far less traffic than it did last week, because of eviction pressure or a change in access patterns. Availability will be green throughout.',
      instead:
        'Alert on hit rate and on origin request rate. A hit-rate drop is an early warning of an origin overload that has not happened yet.',
    },
    {
      mistake: 'Adding retries in front of a cache miss storm.',
      why: 'The origin is overloaded because too many requests arrived at once. Retrying multiplies exactly the traffic that caused it, and turns a recoverable spike into a sustained overload that outlives its trigger.',
      instead:
        'Coalesce misses, shed excess load, and use a retry budget so total retry traffic is bounded regardless of how many requests are failing.',
    },
  ]}
