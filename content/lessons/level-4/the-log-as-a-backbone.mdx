## The problem

A consumer has a bug. For six hours it has been writing the wrong value into a downstream table
for about one message in twenty. Someone notices, the fix is a one-line change, and it ships in
twenty minutes.

Then the real question: how do you repair the six hours?

The messages were delivered and acknowledged, so the broker discarded them. The downstream table
has wrong values with no record of what produced them. The only remaining copies of those events
are in whatever the producers happen to have kept, in a format nobody designed to be re-read.

The fix took twenty minutes. The recovery takes a week of writing one-off scripts, and it is never
quite complete.

## Intuition

There are two ways to move work between machines, and they differ in what happens to a message
after it has been handled.

**A queue is a to-do list.** A worker takes an item, does it, and crosses it off. The list gets
shorter. This is efficient and intuitive, and it has one consequence: **a crossed-off item is
gone.** Only one worker could have taken it, and nobody can do it again.

**A log is a diary.** Events are appended in order and nothing is removed. Each reader keeps a
bookmark saying how far they have read. Several readers can read the same diary at different
speeds for different reasons, and any of them can move their bookmark backwards.

That single change — the reader tracks position, rather than the broker tracking per-message state
— produces almost everything people value in modern messaging:

- **Many independent consumers**, because reading does not consume.
- **Replay**, because the past is still there and the bookmark can move back.
- **A simpler broker**, because appending to a file and serving ranges of it is much less work
  than tracking the state of every message for every consumer.

The cost arrives with it, and it is not small: a diary in strict order can be blocked by one entry
you cannot get past, and a diary has a finite number of pages.

## Concretely

<Example title="The same six-hour bug, with a retained log">

The consumer wrote wrong values for six hours. Now:

1. Fix the bug and deploy the consumer.
2. Move the consumer's offset back six hours.
3. It reprocesses everything since then and overwrites the wrong values with right ones.

Recovery is a configuration change, and it takes as long as reprocessing takes.

**Two conditions make it work, and neither is automatic.**

The processing must be **idempotent** — writing a keyed row, not incrementing a counter. If the
consumer had been adding to a running total, reprocessing would double-count everything, and the
replay would cause a second, worse incident.

The consumer must not have **external side effects that repeat**. If it also sends a confirmation
email, replaying six hours of messages sends six hours of duplicate emails to real people. Replay
is only available to consumers designed for it, which usually means splitting the consumer: one
that updates state, safely replayable; one that sends emails, never replayed.

</Example>

## Formal explanation

<C id="log-based-messaging" /> stores messages in an ordered, append-only sequence, retained for a
configured period, partitioned for parallelism. The broker does not track which messages a
consumer has handled. Consumers do, by recording an <C id="offset">offset</C> — a position in the partition
(<Cite id="kafka-paper" />).

Four consequences follow, and they are the whole subject:

**Ordering exists inside a partition and nowhere else.** Two messages in different partitions have
no defined order, whatever their timestamps say. So the partition key determines what is ordered
with respect to what: key by account id and one account's events stay in order, while different
accounts are independent. Wanting global order means one partition, which means one consumer, which
means no parallelism. That is not a limitation to work around — it is the trade, stated exactly.

**The partition count is the parallelism ceiling.** Within a <C id="consumer-group" />, each
partition is assigned to at most one consumer, so a group can never usefully have more members than
there are partitions. Sixteen partitions means at most sixteen concurrent workers, whatever the
backlog. Partition count is therefore a capacity decision made when the topic is created, and
raising it later changes which key lands where — so anything that depended on a key's history being
in one partition is disturbed.

**Committing the offset is a correctness decision.** Commit before processing and a crash loses the
message: at-most-once. Process before committing and a crash reprocesses it: at-least-once. There
is no local third option, because the offset store and the effect are two different systems. The
familiar conclusion applies again — make the effect idempotent and stop trying to make delivery
exact.

**<C id="replay" /> is the property that changes how you operate.** A consumer bug becomes an
offset reset rather than a data archaeology project. Adding a new consumer that needs history
becomes reading from the beginning rather than a backfill pipeline. This is the single largest
practical difference between a log and a queue, and it is worth designing consumers to preserve it.

Then the costs.

**A <C id="poison-message" /> stops the partition.** In a queue, a message that always fails goes
back to the queue and other work proceeds. In a log, the consumer cannot advance past it without
skipping it, so one unprocessable message halts everything behind it in that partition. This is
head-of-line blocking, and it is a direct consequence of ordering. The answer is an explicit
policy: after N attempts, write the message and its error to a <C id="dead-letter-queue" />,
advance the offset, and alert. A dead-letter destination nobody reads is a data-loss mechanism with
paperwork, so it needs an owner and an alarm.

**Retention bounds everything.** The log is not a database. Retention decides how far back you can
replay, how long a consumer may be down before it loses data, and how long a new consumer's history
goes. It is a disaster-recovery parameter disguised as a storage setting, and the honest way to
express it is: *we can survive a consumer outage of N hours.*

**Scheduling is not a log operation.** &ldquo;Do this in an hour&rdquo; needs random access by due
time; a log gives sequential access by position. Publishing a message an hour early and having the
consumer sleep blocks the partition for an hour. <C id="delay-queue">Delayed execution</C> needs a store
with a time index — which is why the job scheduler in the case study library is built on a
database rather than on a topic, and why the tiered-delay-topic arrangement is a workaround with a
fixed set of delays rather than a general answer.

Finally, the architectural consequence. <C id="event-driven" /> communication means producers stop
knowing who consumes them. You gain the ability to add a consumer without touching the producer,
which is genuinely valuable. You lose the ability to read one call site and know what happens next,
and a change to an event's meaning now breaks consumers you cannot enumerate. The coupling did not
disappear; it moved from the code into the event schema, where it is less visible and therefore
easier to break.

## Trade-offs

<TradeOff
  decision="Use a retained, partitioned log instead of a classic queue"
  options={[
    'Classic queue: broker tracks per-message state, message removed on acknowledgement',
    'Retained log: consumers track offsets, messages retained for a period',
    'Direct synchronous calls between services',
    'A database table polled as a work queue',
  ]}
  why="Replay and multiple independent consumers are properties that cannot be added to a queue afterwards, because the information they need was deleted at acknowledgement time. If you will ever want either, the decision has to be made at the start."
  gain="Reprocessing after a bug becomes an offset reset. New consumers can read history without a backfill pipeline. Producers are decoupled from consumers. Broker throughput is high because appending and serving ranges is cheap work."
  sacrifice="Head-of-line blocking within a partition. Parallelism capped by partition count, chosen up front. Retention storage for data that is usually never re-read. Ordering guarantees that are narrower than most people assume."
  failureModes={[
    'A poison message halting a partition',
    'Lag growing past retention, converting a delay into permanent loss',
    'Replay repeating external side effects',
    'Rebalance storms when processing time exceeds the group timeout',
  ]}
  operationalBurden="Substantial. Per-partition lag monitoring, dead-letter ownership, partition capacity planning, schema compatibility across consumers you may not know about, and a cluster whose storage is sized by retention rather than by throughput."
  cost="Storage for the full retention window plus replication, paid continuously for data that is mostly read once. Usually justified by the single incident where replay turns a week of recovery into an afternoon."
  whenNot="When there is one consumer, work is discarded once done, and nobody will ever reprocess — a queue is simpler and has no head-of-line blocking. When items must be worked in a priority order or with per-item delays, because a log is ordered by arrival and a queue with priorities or a scheduler is the right structure. And when the caller needs an answer, in which case a synchronous call is not a limitation you are working around, it is the correct shape."

## In production

<RealWorld>

<Claim label="fact" source="kafka-paper">
A partitioned log stores messages in order within each partition and retains them for a configured
period. Consumers maintain their own position rather than the broker tracking per-message
acknowledgement, which is what allows multiple independent consumers and re-reading.
</Claim>

<Claim label="fact" source="kafka-docs">
Within a consumer group, each partition is consumed by at most one member, so the number of
partitions bounds the effective parallelism of that group.
</Claim>

<Claim label="fact" source="kafka-docs">
Ordering is guaranteed within a partition, not across partitions. Messages that must be ordered
relative to each other must therefore be assigned the same key.
</Claim>

<Claim label="fact" source="ddia">
Whether an offset is committed before or after processing determines at-most-once or at-least-once
delivery. Both are ordinary outcomes of the ordering, and neither can be avoided by configuration
alone.
</Claim>

<Claim label="convention" source="aws-builders-library">
Bounding retries and moving repeatedly failing messages to a separate destination is established
practice, on the grounds that unbounded retry of a deterministically failing item consumes capacity
without ever succeeding.
</Claim>

<Claim label="convention" source="linkedin-eng">
Published engineering writing on log-centric data infrastructure argues for treating an ordered,
retained log as a primary integration point between systems, so that derived stores can be rebuilt
by reprocessing rather than repaired in place.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Assuming messages are globally ordered.',
      why: 'Ordering holds within a partition only. Events with different keys are unordered relative to each other regardless of the timestamps they carry, and the failure appears only under load when the interleaving changes.',
      instead:
        'Say what must be ordered with respect to what, and make that the key. If nothing must be ordered, say that too — it means you can key for even distribution instead.',
    },
    {
      mistake: 'Treating the log as durable storage.',
      why: 'Retention deletes. A log with seven days of retention is not a record of your business; it is a seven-day buffer, and anything that must outlive that has to be written somewhere designed to keep it.',
      instead:
        'State retention as the maximum survivable consumer outage. If events must be kept permanently, copy them to a store whose job is keeping things.',
    },
    {
      mistake: 'Adding a queue between services to make the system resilient.',
      why: 'It converts a synchronous failure into a growing backlog, which is better only if someone is watching the backlog and the caller can proceed without an answer. If the caller needs the result, an asynchronous hop adds a failure mode and answers nothing.',
      instead:
        'Use asynchrony when the caller genuinely does not need the outcome now. Then commit to monitoring lag, because the backlog is where the failure now lives.',
    },
  ]}
