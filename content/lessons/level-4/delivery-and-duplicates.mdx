## The problem

A payment worker consumes a message, charges a card, and crashes before acknowledging.

The broker, unable to distinguish &ldquo;crashed before doing the work&rdquo; from
&ldquo;crashed after doing the work&rdquo;, redelivers. Another worker charges the card again.

Your broker's documentation says it supports exactly-once semantics. You enabled it. The
customer was still charged twice.

The documentation was not lying. It was describing something narrower than what you assumed, and
the gap between those two things is where the money went.

## Intuition

Imagine posting a letter that must arrive exactly once.

You post it and hear nothing. Did it arrive? You cannot tell. So:

- **Post it again.** It might arrive twice. That is **at-least-once**.
- **Do not post it again.** It might never have arrived at all. That is **at-most-once**.

There is no third option, because the only information you have — silence — is consistent with
both outcomes. No protocol removes this, because any acknowledgement can itself be lost.

But here is the move that solves the practical problem:

**Number the letter.** Send it as many times as you like. The recipient keeps a list of numbers
they have already acted on, and ignores repeats.

Delivery is still at-least-once. The *effect* happens once. That is
<C id="effectively-once">effectively-once</C>, and it is what everyone actually means when they
say exactly-once.

## Concretely

<Example title="What a broker's exactly-once actually covers">

<Claim label="fact" source="kafka-docs">
Kafka provides an idempotent producer, which deduplicates retries of the same produce request,
and transactions, which allow a consume-process-produce cycle to commit atomically — the output
records and the consumer offsets commit together or not at all.
</Claim>

Read that carefully. The guarantee covers **records written back into the same system, plus the
offset commit**. Both are inside the broker's transactional boundary.

Now consider your payment worker:

1. Consume the message. *Inside the boundary.*
2. Charge the card via a third-party API. **Outside the boundary.**
3. Commit the offset. *Inside the boundary.*

The transaction can atomically commit steps 1 and 3. It has no control whatsoever over step 2.
If the process dies between the charge and the commit, the charge happened and the offset did
not move, so the message is redelivered.

**The moment an effect leaves the system's transactional boundary, the guarantee is yours to
build.** That is not a limitation of any particular broker; it is a property of the world.

</Example>

## Formal explanation

Delivery semantics are determined by one decision: **when do you acknowledge?**

- **Acknowledge before processing** → <C id="at-most-once" />. A crash loses the message. No
  duplicates, possible loss.
- **Acknowledge after processing** → <C id="at-least-once" />. A crash redelivers. No loss,
  possible duplicates.

That is the whole design space, and every broker gives you the same choice because it is
inherent rather than implementational.

<C id="exactly-once">Exactly-once delivery</C> is impossible in the general case: it would
require the sender to know whether the receiver acted, which requires an acknowledgement, which
can be lost. But **exactly-once effect** is achievable by combining at-least-once delivery with
an <C id="idempotency">idempotent</C> consumer.

The idempotent consumer needs three things:

1. **A stable identifier** for the unit of work, carried in the message. Not generated by the
   consumer, or a retry generates a different one.
2. **A record of what has been done**, keyed by that identifier.
3. **Atomicity between the effect and the record.** If they can diverge, the guarantee has a
   hole exactly the size of the gap.

When the effect is a write to your own database, requirement three is a single transaction. When
it is external — a card charge, an email — you cannot have one transaction, so you write intent
first, act, then record the outcome, and you need reconciliation for attempts that never reached
a terminal state.

<Callout kind="info" title="The producer side is already solved">
Levels 2 and 3 closed the gap on the producer side: write the message into the
<C id="outbox">transactional outbox</C> in the same transaction as the state change, and publish
from there. That makes publication at-least-once, with no lost events. Everything in this lesson
is about the consumer, which now has to live with the duplicates.
</Callout>

<Deeper title="Ordering is not free either">

<C id="partition-ordering">Ordering is guaranteed within a partition and nowhere else.</C>

To keep two messages ordered relative to each other, they must land in the same partition —
which usually means sharing a partition key. That reintroduces the hot-partition problem: if you
key by account to keep an account's events ordered, a busy account is a hot partition, and its
throughput caps at one partition's throughput.

A useful reframing: **ask whether you need ordering, or whether you need commutativity.**

- &ldquo;Set balance to 100&rdquo; then &ldquo;set balance to 200&rdquo; must be ordered.
- &ldquo;Add 50&rdquo; and &ldquo;add 30&rdquo; can arrive in any order.

Designing operations to commute is often cheaper than enforcing an order across a distributed
system. When it is not possible, a version number on each message lets the consumer reject
anything older than what it has already applied — ordering enforced at the consumer instead of
in transit.

</Deeper>

## Trade-offs

<TradeOff
  decision="Use at-least-once delivery with an idempotent consumer, rather than at-most-once"
  options={[
    'At-most-once: acknowledge before processing',
    'At-least-once plus idempotent consumer',
    'Broker transactions, where the effect stays inside the broker',
  ]}
  why="Losing work silently is almost always worse than doing it twice, and doing it twice can be made harmless with a key and a record. Losing it cannot be made harmless after the fact, because nothing knows it happened."
  gain="No lost work. Retries, rebalances and deploys become safe rather than dangerous. The consumer can be restarted, scaled or redeployed without anyone thinking about in-flight messages."
  sacrifice="Every consumer must carry deduplication logic and a store of processed keys, which is real work and easy to omit in a handler added later. The dedupe store is a new dependency on the processing path."
  failureModes={[
    'A consumer added later without deduplication, reintroducing duplicates on one path',
    'The dedupe record and the effect not being atomic, leaving a window',
    'Keys expiring sooner than the maximum redelivery delay',
  ]}
  operationalBurden="Moderate. A dedupe store to run and expire, and a code review standard that every consumer handles redelivery. The second is harder to sustain than the first."
  cost="One extra lookup and one extra write per message, plus storage for the retention window. Small next to the cost of one duplicate charge."
  whenNot="For genuinely disposable, high-volume telemetry — a metrics sample, a heartbeat — at-most-once is correct: losing one is invisible and deduplicating billions of them costs more than the data is worth. Be explicit that you chose it, so nobody later assumes the pipeline is lossless."
/>

## In production

<RealWorld>

<Claim label="fact" source="kafka-docs">
Kafka's transactional guarantees cover writes back into Kafka together with consumer offset
commits. Effects outside that boundary — writes to another database, calls to a third-party API —
are not covered and must be made idempotent by the application.
</Claim>

<Claim label="convention" source="stripe-eng">
Payment APIs conventionally accept a client-supplied idempotency key and store the result
against it, so that a repeated request returns the original outcome rather than performing the
operation again. This is the standard way to make an external effect safe to retry.
</Claim>

<Claim label="recommendation" source="aws-builders-library">
Assume redelivery will happen and design every consumer for it from the start. Retrofitting
idempotency after a duplicate incident is substantially harder, because the side effects are
already spread across code written on the assumption of a single execution.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'We enabled exactly-once, so duplicates are handled.',
      why: 'The guarantee covers effects inside the broker\'s transactional boundary. A charge, an email, a write to a different database — all outside it. The setting is real and it does not cover the thing you were worried about.',
      instead:
        'Say where the boundary is, and how effects beyond it are made idempotent. That is the actual design.',
    },
    {
      mistake: 'We will deduplicate by hashing the message contents.',
      why: 'Two legitimately identical messages — the same user liking the same post twice, deliberately — are indistinguishable from a redelivery. You will silently drop real work.',
      instead:
        'Use an identifier generated with the intent, so a repeat means a retry and a new intent means a new key.',
    },
    {
      mistake: 'We expire processed keys after an hour to keep the table small.',
      why: 'Redelivery is not always prompt. A consumer group that was down for a day, a message parked and re-driven from a dead-letter queue, or a replay after a bug all deliver old messages again, and a key that has expired cannot recognise them.',
      instead:
        'Keep keys for longer than the longest redelivery you allow, including retention and replay, and write that number down. If the table is too large, that is a storage decision to make deliberately, not a window to shrink silently.',
    },
  ]}
