## The problem

Your application stores users in a table. Looking up a user by ID is instant. Looking up a user
by email address takes 400 milliseconds, and it gets slower every week.

Both are single-row lookups. Both return the same amount of data. The table is the same table.

The difference is that one of those questions has a prepared answer and the other does not, and
understanding why is the difference between someone who uses a database and someone who can
reason about one.

## Intuition

Imagine a filing cabinet holding a million customer records, filed by account number.

&ldquo;Find account 4,721,003&rdquo; is fast. You go straight to the right drawer.

&ldquo;Find the customer whose email is alex@example.com&rdquo; means opening every folder in
every drawer until you find it. A million folders. This is a **full scan**, and it costs time
proportional to how much data you have.

Now suppose you keep a second, thinner set of cards: email address on the front, account number
on the back, sorted alphabetically. Finding an email is now fast — but every time a customer is
added, changed or removed, you have to update the cards too, or they lie to you.

That is an <C id="index" />. A second copy of part of your data, organised for a different
question. It makes some reads dramatically faster and every write slower, and it takes up
space. There is no version of this where the index is free.

## Concretely

<Example title="What it means to get slower every week">

A lookup by primary key uses a structure that stays roughly flat as the table grows: a
B-tree lookup touches a handful of pages whether the table holds a thousand rows or a
billion.

A lookup with no usable index scans. Its cost grows with the table. It was 4 ms when the table
was small, then 40 ms, then 400 ms — and nothing in your code changed. This is the single most
common cause of &ldquo;the application got slow and we do not know why&rdquo;.

The tell is the shape of the graph: query latency rising steadily in proportion to table
growth, with no corresponding change in traffic or deploys.

</Example>

## Formal explanation

Data on disk is organised in **pages** — fixed-size blocks, typically a few kilobytes — because
storage devices and the operating system work in blocks, not in rows. A query's real cost is
roughly the number of pages it must read, not the number of rows it returns.

A <C id="btree">B-tree</C> is a balanced tree of such pages, sorted by key. Finding a key
means descending from the root: a handful of page reads, and the upper levels are almost
always already in memory. This is why the depth barely changes as the table grows, and why
primary key lookups stay fast.

Three properties of a B-tree matter for design:

- **It answers range queries.** Because it is sorted, &ldquo;all orders between March and
  April&rdquo; is a scan along the leaves rather than many separate lookups.
- **It answers prefixes of a composite key.** An index on `(user_id, created_at)` serves
  queries on `user_id` alone, and on both together, but not on `created_at` alone. This one
  fact resolves a large fraction of real-world index confusion.
- **It must be updated on every write** that touches the indexed columns. This is where
  <C id="write-amplification">write amplification</C> comes from: one logical row insert
  becomes one heap write plus one write per index.

The <C id="query-plan">query planner</C> decides how to execute your query, using statistics
about the data. This is why the same query can be fast for months and then suddenly slow: the
statistics changed, or the data distribution did, and the planner made a different choice.

<Claim label="fact" source="postgres-docs">
PostgreSQL's planner chooses among access methods using collected statistics on table
contents, and the chosen plan can be inspected with EXPLAIN. Plan choice depends on estimated
row counts, so stale or skewed statistics can produce a plan that is dramatically worse than
the available alternative.
</Claim>

<Deeper title="Why durability needs a log, not just a write">

When you commit a transaction, the database cannot afford to write every changed page to its
final location immediately: those pages are scattered, and scattered writes are slow.

So it writes the *intent* first, sequentially, to a <C id="wal">write-ahead log</C>, and only
that write has to be durable before the commit can be acknowledged. The actual pages are
updated later, in the background, in a more efficient order.

If the machine dies, recovery replays the log to reconstruct any changes that had not yet
reached their final pages.

This is why sequential writes are the foundation of database durability, and why
<C id="fsync">the point at which the log is actually forced to disk</C> is the true durability
boundary. It is also the mechanism that later makes replication and change data capture
possible: the log already contains an ordered record of every change, so shipping it elsewhere
is nearly free.

</Deeper>

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Query slows steadily as the table grows',
      symptom:
        'Latency climbs in proportion to table size, with no change in traffic or code.',
      cause: 'A full scan where an index lookup was assumed.',
      mitigation:
        'Read the query plan, do not guess. Add the index that serves the actual predicate, and check that the leading columns match how the query filters.',
    },
    {
      what: 'Plan flip',
      symptom:
        'A query that has been fast for months becomes catastrophically slow overnight, with no deploy.',
      cause:
        'Statistics changed, or the data distribution did, and the planner chose a different access method. Common after a bulk load or a big deletion.',
      mitigation:
        'Keep statistics current. Alert on query latency per statement rather than only in aggregate, so a single plan flip is visible.',
    },
    {
      what: 'Too many indexes',
      symptom:
        'Writes are slow and storage is much larger than the data. Read performance is fine.',
      cause:
        'Every index is maintained on every write. Indexes accumulate over years and are rarely removed.',
      mitigation:
        'Audit index usage. Most databases can report which indexes are never used; those are pure cost.',
    },
    {
      what: 'Working set stops fitting in memory',
      symptom:
        'A sudden, severe performance change with no obvious trigger. Disk read rate jumps sharply.',
      cause:
        'The hot pages no longer fit in the page cache, so reads that were memory accesses become disk accesses — orders of magnitude slower.',
      mitigation:
        'Monitor cache hit ratio as a leading indicator, not database latency as a lagging one. This is a cliff, not a slope.',
    },
  ]}

## Trade-offs

<TradeOff
  decision="Add a secondary index to make a slow query fast"
  options={[
    'Add the index',
    'Change the query or the access pattern so an existing index serves it',
    'Cache the result of the query instead',
    'Accept the scan, because the table is small and will stay small',
  ]}
  why="An index converts a scan into a handful of page reads, which is usually orders of magnitude and often the difference between viable and not. When the query is frequent and the table is large, nothing else comes close."
  gain="Read latency becomes roughly independent of table size for that access pattern, and stays that way as the data grows."
  sacrifice="Every write that touches the indexed columns now maintains an additional structure. Storage grows. Write latency rises, and write throughput falls."
  failureModes={[
    'An index on a low-cardinality column that the planner correctly refuses to use: pure cost, no benefit',
    'An index whose leading column does not match how queries filter, which therefore cannot be used',
    'Index bloat over time from update-heavy tables, needing periodic maintenance',
  ]}
  operationalBurden="Building an index on a large live table takes time and resources, and a naive build can lock the table. Most engines offer a concurrent build; use it, and know how long it will take before you start."
  cost="Storage proportional to the indexed columns plus overhead, and a measurable share of write throughput. On a write-heavy table with many indexes, index maintenance can exceed the cost of the row write itself."
  whenNot="When the table is small enough that a scan is genuinely cheap, an index adds write cost for no measurable read benefit. When the query is rare — a monthly report — the right answer is usually to run it against a replica or an analytical store rather than to slow every write to serve it."
/>

## In production

<RealWorld>

<Claim label="fact" source="postgres-docs">
PostgreSQL supports several index types with different capabilities: B-tree for equality and
range on ordered types, hash for equality only, GIN and GiST for containment and full-text,
and BRIN for very large naturally-ordered tables. Choosing the type is part of choosing the
index, not an afterthought.
</Claim>

<Claim label="fact" source="database-internals">
B-trees update pages in place, which produces random writes, while log-structured merge trees
buffer writes in memory and flush sorted files, producing sequential writes at the cost of
read amplification and ongoing compaction. Neither is universally better; the choice follows
the workload.
</Claim>

<Claim label="recommendation">
Read the query plan before adding an index. The planner will tell you what it is doing and
what it estimates; guessing produces indexes that are never used and whose write cost you pay
forever.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'The query is slow, so we should shard the database.',
      why: 'Sharding gives each machine less data; it does not make a query faster. A scan is still a scan, now running on many machines with a scatter-gather on top, and you have given up joins and transactions to get there.',
      instead:
        'Read the plan. Almost always the answer at this stage is an index, a query change, or a bigger machine. Sharding is for when one node cannot hold the data or sustain the write rate.',
    },
    {
      mistake: 'We added indexes on every column so any query will be fast.',
      why: 'Write throughput is now a fraction of what it was, storage has multiplied, and most of those indexes will never be chosen by the planner anyway.',
      instead:
        'Index the access patterns you actually have. Composite indexes matching real query shapes beat many single-column indexes.',
    },
    {
      mistake: 'We will cache the query result instead of fixing the index.',
      why: 'You have added staleness, a stampede risk, and a new dependency, to avoid writing one line of DDL. And the first cache miss still pays the full scan.',
      instead:
        'Fix the read first. Cache what is genuinely expensive to compute, not what is expensive only because it was never indexed.',
    },
  ]}
/>
