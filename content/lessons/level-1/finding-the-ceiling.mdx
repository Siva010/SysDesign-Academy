## The problem

A team is designing a new service. Expected load: 500 requests per second, growing to maybe
2,000 within two years. The design document proposes a sharded database, a message queue, a
cache tier, and four microservices.

Nobody in the room asks the question that would collapse the whole thing: **what can one
machine do?**

It is not a rhetorical question with a flattering answer. It has a number, the number is
usually larger than people expect, and finding it is the cheapest architectural work
available.

## Intuition

Distribution is not a free upgrade. It is a trade: you give up simplicity, transactions,
easy debugging and cheap operations, and you get past a limit you had actually reached.

If you have not reached the limit, you paid the price and got nothing.

So the first job is to find the ceiling. Not to guess it, and certainly not to infer it from
the fact that a large company built something complicated — they had a different limit and a
different number of engineers.

There is a second, subtler point. A machine does not have *one* ceiling. It has several, and
they are hit in an order that depends on your workload:

- **CPU**, if you compute per request.
- **Memory**, if your working set is large or per-connection state is heavy.
- **Disk I/O**, if the working set does not fit in memory.
- **Network**, if you move large payloads.
- **Concurrency limits** — connections, descriptors, pool slots — which usually arrive first.

Finding the ceiling means finding which of these you hit, at what load, and what the graph
looks like as you approach it.

## Concretely

<Example title="What a single machine can plausibly do">

The honest answer to &ldquo;how many requests per second can one server handle&rdquo; is
&ldquo;measure it&rdquo;, because it depends entirely on what a request does. But the range is
worth internalising, because intuition is usually off by an order of magnitude in the
pessimistic direction.

<Claim label="recommendation">
Rather than memorising figures that go stale, derive your own once and keep it. Take one
machine, run your real workload against it, and record: requests per second at your latency
objective, which resource saturated first, and how latency behaved as you approached it. That
single measurement is worth more than any table, and it is the number every capacity
conversation for the next two years will reference.
</Claim>

Two things reliably surprise teams that do this:

1. The number is higher than expected, often by a lot. Modern hardware is very fast and
   modern databases are very good.
2. The resource that runs out first is rarely CPU. It is usually a bounded pool, a
   connection limit, or the working set no longer fitting in memory.

</Example>

## Formal explanation

The ceiling is set by the first resource to saturate, which is the definition of a
<C id="bottleneck" />. Two things follow.

**Optimising anything else is wasted.** If disk I/O is the constraint, a faster CPU changes
nothing. This is why the USE method — for each resource, examine utilisation, saturation and
errors — is the standard investigation order: it forces you to look at every resource rather
than the one you suspect.

**Fixing the bottleneck moves it.** Removing the disk constraint reveals the CPU constraint.
Capacity work is iterative by nature, and knowing that keeps expectations honest.

The second concept is <C id="capacity-headroom" />: the distance between normal load and the
point where latency stops being acceptable. It matters because that gap is the only thing
absorbing a spike. Autoscaling reacts in minutes; a traffic spike arrives in seconds. Headroom
is what carries you until capacity arrives, and it is why a system running at 90% utilisation
is not efficient but fragile.

<Deeper title="Why vertical scaling is underrated">

<C id="vertical-scaling">Vertical scaling</C> has a reputation as the amateur option. The
reputation is undeserved, and the case for it is specific:

- **It preserves everything.** Transactions, joins, single-node consistency, one place to look
  during an incident. Every one of those is expensive to give up.
- **It is instant and reversible.** Resizing is a maintenance window. Sharding is a project
  measured in quarters, and it is very hard to undo.
- **The hardware has moved.** Machines available today have core counts and memory sizes that
  make many "we must distribute" arguments from a decade ago simply obsolete.

The genuine limits are real and worth naming: there is a largest machine, a single machine is
a single failure domain, and cost per unit of capacity rises at the top of the range.

<Claim label="recommendation">
The useful sequence is: measure, optimise the bottleneck, scale vertically, add read replicas,
and only then partition. Most systems never reach the last step, and the ones that do arrive
there with a much better understanding of their workload than they would have had at the start.
</Claim>

</Deeper>

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Distributing before measuring',
      symptom:
        'A complex architecture with modest traffic, slow feature delivery, and incidents nobody can debug quickly.',
      cause:
        'The distribution decision was made from anticipated scale that never arrived, or from imitation of a much larger company.',
      mitigation:
        'Measure the single-machine ceiling first. Write the number down. Revisit the decision when you are within a factor of three of it.',
    },
    {
      what: 'Load testing an unrealistic workload',
      symptom:
        'The load test says 20,000 requests per second; production falls over at 3,000.',
      cause:
        'The test used a uniform key distribution, a warm cache, small payloads, or no think-time between requests. Real traffic is skewed and bursty.',
      mitigation:
        'Replay real traffic shapes, including the skew. Test with a cold cache too, because that is the state you will be in during an incident.',
    },
    {
      what: 'Running at the knee to save money',
      symptom:
        'Latency is acceptable on average and terrible whenever anything varies: a deploy, a backup, a traffic burst.',
      cause: 'No headroom, so ordinary variability has nowhere to go.',
      mitigation:
        'Choose a target utilisation deliberately, informed by how bursty your traffic is, and treat sustained operation above it as a capacity problem rather than a monitoring nuisance.',
    },
    {
      what: 'Single machine as a single failure domain',
      symptom: 'Total outage from one hardware fault or one bad process.',
      cause:
        'Vertical scaling improves capacity and does nothing for availability.',
      mitigation:
        'Run at least two, even if one could serve all the traffic. Redundancy and capacity are separate reasons to add a machine, and conflating them leads to designs that are fast and fragile.',
    },
  ]}

## Trade-offs

<TradeOff
  decision="Scale vertically until measurement shows a single machine cannot meet the requirement"
  options={[
    'Design for horizontal scale from day one',
    'Scale vertically, add read replicas, partition only when measurement demands it',
    'Serverless or managed services that abstract the machine entirely',
  ]}
  why="Distribution costs consistency, debuggability and operational simplicity. Those are worth paying for when you have hit a real limit, and pure loss when you have not. Measurement is what distinguishes the two cases."
  gain="Transactions across your whole dataset, joins, one place to look during an incident, and a much smaller surface area for a small team. Feature delivery is faster because there is less coordination."
  sacrifice="A hard ceiling exists, and you will hit it eventually if you grow enough. Migration at that point is a real project, and it lands when you are busy."
  failureModes={[
    'The ceiling arrives faster than expected and the migration is done under pressure',
    'A single machine is a single failure domain, so availability needs a separate answer',
    'Some workloads have no vertical answer at all: petabyte datasets, or genuinely global latency requirements',
  ]}
  operationalBurden="Much lower than any distributed alternative. One system to back up, upgrade, monitor and reason about. This is the largest and least-quantified benefit."
  cost="Cost per unit of capacity rises at the top of the machine range, so the largest instances are poor value per core. Below that range it is typically far cheaper than a distributed equivalent, once engineering time is counted."
  whenNot="When the dataset genuinely does not fit, when write throughput genuinely exceeds one node, when regulation requires data in multiple jurisdictions, or when availability requirements cannot tolerate a single failure domain and the failover story needs a distributed design anyway. Also when the growth curve is steep and known: migrating at 10x is much harder than designing for it at 1x, and that argument is legitimate when the growth is real rather than aspirational."

## In production

<RealWorld>

<Claim label="convention" source="brendan-gregg">
The USE method — utilisation, saturation and errors for every resource — is standard practice
for capacity investigation because it prevents the common failure of examining only the
resource you already suspect.
</Claim>

<Claim label="convention" source="sre-book">
Capacity planning based on measured per-unit cost, with deliberate headroom for variability,
is standard reliability practice. The alternative — provisioning from intuition and reacting
to incidents — produces systems that are simultaneously over-provisioned and fragile.
</Claim>

<Claim label="recommendation">
Run the single-machine measurement before the architecture review, not after. It is a day of
work and it frequently changes the decision, because the number is usually larger than the
room assumed.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'We designed for scale from the start.',
      why: 'Designing for scale you do not have means paying its costs — distributed transactions, eventual consistency, harder debugging, slower delivery — for a benefit that is entirely hypothetical. Meanwhile the actual constraint is usually delivery speed.',
      instead:
        'Design so that scaling is possible later: clean boundaries, no assumptions about single-node ordering, an identifier scheme that survives partitioning. Then build the simple thing.',
    },
    {
      mistake: 'A single database will not handle this.',
      why: 'Usually stated without a number. Modern single-node databases handle workloads that would have needed a cluster a decade ago, and the person saying this rarely knows the current figure.',
      instead:
        'Give the number you expect and the number you believe a machine can do. If they are within a factor of three, that is a real argument; if they are two orders apart, the conversation should stop.',
    },
    {
      mistake: 'We run at 90% utilisation, which is efficient.',
      why: 'It is efficient in the sense that a car with no crumple zone is light. Queueing delay rises steeply near saturation, so ordinary variability now produces user-visible latency, and there is nothing left to absorb a spike.',
      instead:
        'Choose a target utilisation from your traffic burstiness, and treat the gap as bought insurance rather than waste.',
    },
  ]}
