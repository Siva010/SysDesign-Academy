## The problem

Someone splits the order code and the pricing code into two services. The call site barely changes:

    price = pricing.quote(item, customer)

One line, same shape as before. The team ships it.

A month later the order page is slow, and nobody can say why. It turns out that rendering a cart
of twelve items calls pricing twelve times, sequentially. Then pricing has an incident, and orders
stop — not because orders are broken, but because a call that used to be a jump within one process
now has a way to fail. Then someone renames a field, and a service that was not redeployed starts
returning nulls.

Nothing here is a bad decision in isolation. All of it follows from one line of code looking
unchanged while everything underneath it changed.

## Intuition

Asking a colleague sitting next to you a question is instant and reliable. If they hear you, they
answer. If they do not, you notice immediately.

Asking a colleague in another building is a different act, even though the sentence is identical.
It takes time. They might be at lunch. Your message might arrive and their reply might not, and
from where you are sitting those two look exactly the same. If you have twelve questions you would
walk over once and ask all twelve, not walk twelve times.

The mistake is not going to the other building. Sometimes you must. The mistake is **using the same
sentence and expecting the same experience**, and writing code as though the distance is a detail.

Four things change the moment a call leaves the process, and none of them are visible at the call
site:

- **Time.** Nanoseconds become milliseconds. Four orders of magnitude.
- **Partial failure.** A local call either happens or throws. A remote call can time out after the
  work was done, and you cannot tell which.
- **Types.** A compiler checked the local call. Nothing checks the remote one at build time unless
  you deliberately arrange it.
- **Deployment.** The two sides now ship separately, so at every moment some caller is running
  against a version of the interface that is not the current one.

## Concretely

<Example title="The same page, three interface shapes">

A cart page needs, for each of twelve items, a price, a stock figure and a name.

**Twelve sequential calls.** Each round trip is 20 ms, so 240 ms of pure waiting before rendering
begins. Nothing is slow — every service responds promptly — and the page is slow anyway. This is
the n+1 problem, and its distinguishing symptom is that no individual component looks unhealthy.

**One batched call.** `quote(items, customer)` takes a list and returns a list. One round trip:
20 ms. The saving is not efficiency, it is a change of shape — the interface now accepts the
question the caller actually has instead of a piece of it.

**One flexible query.** The client asks for exactly the fields it wants across several entities and
the server assembles the response. The over-fetching problem disappears from the wire — and moves
inside the server, which must now avoid making twelve internal calls to serve one external one.
The n+1 problem is not solved by the query language; it is relocated to where it is less visible.

</Example>

## Formal explanation

Start from the baseline. A <C id="monolith" /> is one deployable unit where calls between modules
are in-process. Its properties are frequently misremembered as weaknesses: calls are free, refactoring
across a boundary is a compiler-checked operation, and there is no partial failure between modules.
Those are strong properties, and splitting a system gives every one of them up. The reason to split
is that separate teams can deploy separately and scale separately — an organisational and
operational benefit purchased with a technical cost, not a technical improvement.

<C id="rpc" /> makes a remote call look like a local one. Historically that was the explicit goal,
and it is exactly where the trouble comes from: the abstraction hides latency and partial failure,
which are the two things a caller most needs to know about.

<C id="grpc" /> is a modern instance that keeps the local-call shape while being honest about the
rest: an interface definition generates client and server code, so the contract is checked at build
time; it uses a compact binary encoding, so payloads are small; and it uses long-lived multiplexed
connections, so many calls share one connection without queueing behind each other. The cost is
that the contract is a build-time artefact — callers need generated code, and browsers cannot
speak it without a translating proxy.

REST over HTTP takes the opposite position. The unit is a resource, the operations are the HTTP
methods, and the contract is a document rather than a compiler. It is inspectable, cacheable by
ordinary intermediaries (<Cite id="rfc9110" />), and works everywhere — at the price of a chatty
shape, because one resource per request is the model.

<C id="graphql" /> moves the choice of what to fetch to the client, which removes over-fetching and
under-fetching from the wire in one step. What it gives up is worth stating plainly: response
caching by intermediaries largely stops working, because the response depends on a query rather
than on a URL; and the server's cost per request becomes unpredictable, because clients can now
ask for expensive things.

Two failure patterns cut across all of these.

The <C id="n-plus-one" /> problem: fetching a list, then making one call per element. It appears
identically in a database (one query per row), in a service mesh (one call per item) and in a
GraphQL resolver (one lookup per field). The fix is always the same shape — **make the interface
accept the whole question** — which is what <C id="batching" /> means here. Batching is not a
performance trick applied afterwards; it is an interface design decision that has to be available
in the contract.

And <C id="versioning" />. Once two sides deploy independently, every change is live alongside the
version before it. Additive changes — new optional fields, new endpoints — are safe. Removals and
meaning changes are not, and they need the expand-contract sequence: add the new thing, migrate
callers, verify nobody uses the old thing, then remove it. Skipping the verification step is how
you discover which internal client nobody documented.

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'N plus one across a service boundary',
      symptom: 'A page is slow while every service reports healthy latency and no errors.',
      cause: 'A loop makes one remote call per item, so page latency is the item count times the round trip.',
      mitigation: 'Batch the interface so it accepts a list. Detect it by counting downstream calls per inbound request, which is the metric that makes it visible.',
    },
    {
      what: 'Ambiguous timeout',
      symptom: 'A duplicate charge, a duplicate order, or two identical records created seconds apart.',
      cause: 'A call timed out after the work completed. The caller retried, and the callee had no way to recognise the retry.',
      mitigation: 'Accept an idempotency key on any operation with an effect. A remote call needs a defined answer for "no reply", and the only safe ones are retry-with-a-key or fail.',
    },
    {
      what: 'Silent contract drift',
      symptom: 'A field is null in production and nowhere in any test.',
      cause: 'The producer changed the meaning or optionality of a field, and nothing enforces the contract at build time across two independent deployments.',
      mitigation: 'A machine-checked schema plus contract tests run against the real producer. A written specification is not a check.',
    },
    {
      what: 'Availability multiplied',
      symptom: 'Your service misses its target although your own code never fails.',
      cause: 'Every synchronous dependency multiplies into your availability, and the arithmetic was never done.',
      mitigation: 'Make dependencies optional where the product allows — a cached price, a default, a degraded panel — so a failure downgrades the response rather than failing it.',
    },
    {
      what: 'Unbounded query cost',
      symptom: 'One client request occupies the server for seconds and the pattern is not in any dashboard.',
      cause: 'A flexible query language lets a client request an expensive traversal that no endpoint would ever have exposed.',
      mitigation: 'Query depth and complexity limits, per-client cost budgets, and persisted queries so only known shapes are accepted.',
    },
  ]}

## Trade-offs

<TradeOff
  decision="Expose a batched, coarse-grained interface rather than fine-grained per-entity calls"
  options={[
    'Fine-grained resources: one call per entity, cacheable and simple',
    'Batched operations: the interface accepts and returns lists',
    'A flexible query language: the client states exactly what it needs',
    'Keep it in one process: no interface at all',
  ]}
  why="Remote calls cost a round trip each, and callers almost never want exactly one entity. An interface built around single entities forces every caller into a loop, and the loop is invisible at the call site where it is written."
  gain="Page latency stops scaling with item count. Downstream call volume falls by the batch factor. The interface now expresses the question callers actually have, which usually also makes it easier to read."
  sacrifice="Coarse responses cache poorly, because a batch of twelve is not a reusable cache entry. Partial failure within a batch needs a defined answer. And a coarse interface leaks the caller's use case into the producer's contract, which couples them more tightly."
  failureModes={[
    'One bad element failing an entire batch, or a partial result the caller ignores',
    'Batch size unbounded, so a caller can request ten thousand items and occupy the server',
    'Cacheability lost, which sometimes costs more than the round trips saved',
  ]}
  operationalBurden="Low. The real burden is design discipline: batch endpoints multiply as callers appear with slightly different needs, and without care the interface becomes one endpoint per screen."
  cost="Negligible directly. The indirect cost is coupling, because each batch shape encodes a caller's needs into the producer's contract."
  whenNot="When responses are highly cacheable and mostly hit — a fine-grained resource served from cache beats a batch that must be computed. When callers genuinely want one entity at a time. And when the two components are not separately deployed or separately scaled, in which case the correct interface is a function call in one process, and introducing a network boundary buys latency, failure modes and versioning work for nothing."
/>

## In production

<RealWorld>

<Claim label="fact" source="rfc9110">
HTTP defines which methods are safe and which are idempotent. A safe method is expected not to
change state, and an idempotent method may be repeated with the same effect as a single
invocation. These properties are what allow intermediaries to cache and retry without coordination.
</Claim>

<Claim label="convention" source="building-microservices">
Splitting a system into independently deployable services is presented as an organisational and
operational decision with real technical costs — network latency, partial failure, and versioning
across independent deployments — rather than as a technical improvement in itself.
</Claim>

<Claim label="convention" source="fundamentals-arch">
Interface granularity is described as a primary architectural decision: fine-grained interfaces
produce chatty communication and coupling through call volume, while coarse-grained interfaces
couple through shared shapes. Neither direction is free.
</Claim>

<Claim label="convention" source="martin-fowler">
The observation that a remote call cannot be made to look like a local one — because latency,
partial failure and independent evolution are visible to the caller whether or not the syntax
hides them — is long-standing and widely repeated in architecture writing.
</Claim>

<Claim label="fact" source="ddia">
Independently deployed services mean old and new versions of code and data formats coexist in
production. Compatibility must therefore run in both directions: new code reading old data, and
old code reading data written by new code.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Splitting into services because it is the modern architecture.',
      why: 'Every boundary adds a round trip, a failure mode, a deployment dependency and a versioning obligation. Those are paid immediately; the benefits — independent deploys, independent scaling, team autonomy — only arrive if separate teams actually own the pieces.',
      instead:
        'Name what the boundary buys in this specific system. If the answer is not about deployment, scaling or ownership, the boundary is a cost with no purchaser.',
    },
    {
      mistake: 'Treating a timeout as a failure.',
      why: 'A timeout means you do not know. The work may have completed and the reply been lost. Retrying an unknown outcome without an idempotency key is how one action becomes two.',
      instead:
        'Classify outcomes as success, definite failure, and unknown. Give the unknown case an explicit design: an idempotency key, a reconciliation pass, or a decision to fail rather than retry.',
    },
    {
      mistake: 'Versioning by putting v2 in the URL and hoping.',
      why: 'A version number does not tell you when v1 can be removed. Without knowing who still calls it, the old version lives forever and every change is made twice.',
      instead:
        'Prefer additive change. When a break is unavoidable, run both, instrument usage of the old path per caller, and remove it only when the number reaches zero and stays there.',
    },
  ]}
/>
