## The problem

A message arrives for a user who is looking at their screen right now. Nothing happens.

The interface has no way to know. It asked the server for messages four seconds ago and got
nothing, and it will ask again in another four. The information exists, it is one hop away, and it
sits there because the conversation only runs one way: the client asks, the server answers.

So you make it ask more often. Every second, from every open tab. Now a service with 200,000 idle
users is handling 200,000 requests per second to say &ldquo;nothing new&rdquo;, and the answer is
still up to a second late.

## Intuition

There are exactly two ways to learn something someone else knows.

**You ask them, repeatedly.** Cheap to arrange, and you pay for every question, including all the
ones answered &ldquo;nothing&rdquo;. Your worst-case delay is the gap between questions.

**They keep a line open and tell you.** No wasted questions, and news arrives immediately. But
somebody has to hold the line open, and the cost of holding it is paid whether or not anything is
ever said.

Neither is free and neither is universally better. Polling converts *freshness* into *request
volume*: the fresher you want to be, the more you ask. Pushing converts freshness into *connection
count*: the cost no longer depends on how often anything happens, only on how many people are
listening.

That is the actual trade, and it means the right answer depends on a ratio you can compute — how
often does something happen, per connected user? Rare events with many idle users favour polling.
Frequent events favour pushing. A chat application and a stock ticker sit at opposite ends and
should not use the same mechanism.

## Concretely

<Example title="Four ways to learn about a new message, with their real costs">

Assume 200,000 connected users and, on average, one relevant event per user per five minutes.

**Poll every 4 seconds.** 50,000 requests per second, of which about 99.7% return nothing. Each
carries request headers, authentication and a connection. Worst-case staleness: 4 seconds.

**Poll every 60 seconds.** 3,300 requests per second — sixteen times cheaper, and now the product
feels broken for anything conversational. This is the dial, and it only has these two ends.

**Long polling.** The client asks and the server *holds the request open* until there is something
to say or a timeout expires. Delivery is immediate, wasted requests disappear, and the cost moves:
the server is now holding 200,000 open requests. It has become a stateful service using an HTTP
shape.

**A persistent connection.** One connection per user, held open, with messages sent in either
direction whenever either side has something to say. Delivery is immediate and per-message
overhead is a few bytes rather than a full request.

The last two cost nearly the same thing, and it is not bandwidth. It is 200,000 open sockets, and
everything that follows from a tier that remembers who is attached to it.

</Example>

## Formal explanation

HTTP is request-response: a client sends a request, a server sends a response
(<Cite id="rfc9110" />). A server has no way to originate a message to a client that has not
asked, because there is no channel to originate it on.

Three mechanisms work around this, and they differ in what they cost rather than in what they
achieve:

- **Polling.** Repeated ordinary requests. Simple, stateless, works through every intermediary
  ever built. Cost is proportional to *clients × poll rate*, independent of how much actually
  happens.
- **Long polling.** A request the server does not answer until it has something to say. Delivery
  is immediate; the server holds an open request per client.
- **A persistent connection**, such as a <C id="websocket" /> upgraded from an HTTP request
  (<Cite id="rfc6455" />), or a one-directional server-sent event stream. Either side may send at
  any time, with minimal per-message overhead.

<C id="push-vs-pull" /> is the underlying choice, and the consequence that matters is not on the
wire. It is this:

**A pushing tier is stateful.** The server holding your connection is *the* server that must
deliver your messages. That single fact undoes several properties you were relying on:

- **Load balancing changes meaning.** Balancing connections is not balancing work. A machine with
  an even share of connections may hold an uneven share of the active ones, and the imbalance
  persists because connections do not move.
- **Deploys become disruptive.** Restarting a machine drops every connection it holds. Those
  clients all reconnect at once, to the machines that are still up, which are now carrying more
  than their share.
- **Delivery needs routing.** To send a message to a user, something must know which machine holds
  that user's connection. That is a registry, and it is a new piece of infrastructure with its own
  staleness and its own failure modes.
- **Capacity is measured in connections.** Sockets, file descriptors and per-connection memory are
  consumed by idle users. Your ceiling is now the number of people connected, not the amount of
  work being done.

None of these is a reason to avoid pushing. They are the bill, and it should be read before
signing.

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Reconnect storm',
      symptom: 'A brief network blip becomes a long outage. The service is fine until everyone comes back at once.',
      cause: 'Every disconnected client retried immediately, and on the same schedule, against a tier sized for steady state.',
      mitigation: 'Randomised backoff on the client, plus a server-directed retry delay so the server retains control during the event. Reconnect capacity is a separate number from steady-state capacity.',
    },
    {
      what: 'Connection exhaustion',
      symptom: 'New connections are refused while CPU and memory look unremarkable.',
      cause: 'File descriptor limits, ephemeral port ranges, or per-connection buffers were the real ceiling.',
      mitigation: 'Measure the limit deliberately rather than discovering it. Connections are a capacity dimension with its own units.',
    },
    {
      what: 'Silent half-open connection',
      symptom: 'A client shows as connected and receives nothing. The server believes it delivered.',
      cause: 'The path died without either endpoint being told. TCP does not notice an idle connection has failed.',
      mitigation: 'Application-level heartbeats in both directions with a timeout, and treat a missed heartbeat as a disconnection rather than waiting for the operating system.',
    },
    {
      what: 'Uneven connection load',
      symptom: 'One gateway saturates while others idle, and the imbalance persists for hours.',
      cause: 'Connections were balanced at establishment and never move. A gateway that came up after a deploy has fewer, and keeps fewer.',
      mitigation: 'Balance on connection count rather than round-robin, and expire connections deliberately so the distribution can be corrected.',
    },
    {
      what: 'An intermediary closes idle connections',
      symptom: 'Connections drop after exactly 60 seconds of silence, only on some networks.',
      cause: 'A proxy or NAT device between client and server reclaims idle state on a timer.',
      mitigation: 'Periodic keepalive traffic below the shortest timeout you encounter. This is why heartbeats exist for two reasons rather than one.',
    },

## Trade-offs

<TradeOff
  decision="Hold a persistent connection per user instead of polling"
  options={[
    'Poll on a timer: simple, stateless, costs requests',
    'Long poll: immediate delivery over ordinary HTTP, still holds a request per client',
    'Server-sent events: one-directional push, ordinary HTTP, automatic reconnection',
    'WebSocket: bidirectional, low per-message overhead, a fully stateful tier',
  ]}
  why="When events are frequent enough that most polls would return something, or when delivery latency is the product, the wasted request volume and the latency floor of polling both stop being acceptable. Below that threshold, polling is genuinely the better engineering."
  gain="Immediate delivery. Per-message overhead of a few bytes rather than a full request with headers and authentication. Request volume becomes proportional to events rather than to users times poll rate."
  sacrifice="The connection tier becomes stateful. Deploys drop connections, delivery needs a registry, load balancing no longer balances work, and idle users consume capacity."
  failureModes={[
    'Reconnect storms after any network event or deploy',
    'Connection exhaustion at limits nobody measured in advance',
    'Half-open connections that appear healthy and deliver nothing',
    'Connection imbalance that persists because connections do not move',
  ]}
  operationalBurden="High relative to polling. A new tier with its own scaling metric, a registry to keep correct, a deploy strategy that accounts for mass reconnection, and heartbeats that must be tuned against intermediaries you do not control."
  cost="Memory and descriptors per idle connection, paid continuously. For many idle users and rare events this is strictly worse than polling, and the arithmetic is easy to do before committing."
  whenNot="When events are rare relative to connected users — a notification a user receives twice a day does not justify holding their socket open all day. When the client is a mobile device, where a held connection costs battery and the platform push service does the job better. When one-directional push suffices, server-sent events cost far less than a WebSocket. And whenever the polling interval that satisfies the product is more than a few seconds, in which case polling is the simpler correct answer."
/>

## In production

<RealWorld>

<Claim label="fact" source="rfc6455">
The WebSocket protocol establishes a full-duplex connection over a single TCP connection by
upgrading from an HTTP request, so that either endpoint may send at any time with a small
per-message framing overhead.
</Claim>

<Claim label="fact" source="rfc9110">
HTTP is a stateless request-response protocol in which a server responds to requests it receives.
There is no mechanism for a server to originate a message to a client that has not made a request.
</Claim>

<Claim label="fact" source="mdn-http">
Server-sent events provide a one-directional stream from server to client over ordinary HTTP, with
automatic reconnection and event identifiers for resuming, and are simpler to operate than a
bidirectional connection where the client does not need to send.
</Claim>

<Claim label="convention" source="hpbn">
Long-lived connections consume server resources whether or not data flows, so connection count
becomes an independent capacity dimension alongside request rate and bandwidth.
</Claim>

<Claim label="convention" source="discord-eng">
Published engineering writing on large real-time messaging systems describes a dedicated
connection-handling tier separate from application logic, together with explicit handling of mass
reconnection, as a primary architectural concern rather than a tuning detail.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Using WebSockets because the feature is described as real-time.',
      why: '"Real-time" in a product conversation usually means "within a few seconds", which polling satisfies at a fraction of the operational cost. The word describes a feeling, not a latency budget.',
      instead:
        'Ask for the acceptable staleness in seconds and the event rate per user. Those two numbers decide it, and they usually decide it against the persistent connection.',
    },
    {
      mistake: 'Treating the connection tier as stateless because the application behind it is.',
      why: 'The connection is state, held on one specific machine. Deploys, autoscaling and load balancing all behave differently once that is true, and the design has to say how messages are routed.',
      instead:
        'Draw the registry that maps users to gateways, and say what happens to it during a deploy. If you cannot, the design is incomplete rather than simple.',
    },
    {
      mistake: 'Assuming a connection is alive because it has not reported an error.',
      why: 'A path can fail silently. TCP will not detect a dead idle connection for a very long time, and an intermediary may have discarded its state without telling either end.',
      instead:
        'Heartbeat in both directions with an explicit timeout, and treat missed heartbeats as disconnection. This also keeps intermediaries from reclaiming an idle connection.',
    },
  ]}
