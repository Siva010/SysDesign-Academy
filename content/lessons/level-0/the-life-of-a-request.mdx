## The problem

Someone in São Paulo taps a link to your site. Two and a half seconds later, the page appears.
Your server logs say the request took 40 milliseconds.

Both numbers are correct. The gap between them is where system design lives.

If you cannot account for those missing 2.46 seconds, every optimisation you attempt is a
guess. You will add a cache to a system whose problem was three sequential network round
trips. You will buy faster servers to fix a delay that happened before any server was
involved.

So: what actually happens between the tap and the pixels?

## Intuition

Sending a request over the internet is less like calling a function and more like sending a
courier to another city.

Before the courier can carry anything, several things must happen. You need the address —
someone has to look it up. The courier has to travel there, and physically cannot arrive
faster than the road allows. If the contents are private, you and the recipient must first
agree on a sealed envelope, which itself takes a trip or two. Only then does your actual
message travel.

Each of those steps is a round trip. The distance is fixed by geography. Your code runs at
the very end, and often accounts for the smallest part of the total.

This is the single most important reframing in this whole curriculum: **most of the time in
a request is spent waiting, not computing.** Design accordingly.

## Concretely

<Example title="One tap, step by step">

A user in São Paulo requests `https://example.com/dashboard`. The server is in Virginia,
roughly 7,600 km away.

1. **Is it cached locally?** The browser checks its own cache. A hit here costs microseconds
   and the story ends. Assume a miss.
2. **What address?** The browser asks a DNS resolver for `example.com`. If the answer is
   cached nearby, this is fast. If not, the resolver walks the DNS hierarchy — root, then
   `.com`, then the domain's own nameservers — which can be several round trips.
3. **Open a connection.** TCP requires a handshake before any application data flows: one
   round trip.
4. **Agree on encryption.** TLS 1.3 completes its handshake in one further round trip on a
   fresh connection.
5. **Send the request.** Now, finally, the HTTP request travels: another half round trip out.
6. **The server works.** Parse, authenticate, query the database, render. This is the 40 ms
   in your logs.
7. **The response returns.** Half a round trip back, plus however long the bytes take to
   stream at the available bandwidth.
8. **The browser renders**, discovers it needs three more files, and — depending on what
   those are and where they live — may repeat parts of this whole process.

</Example>

The physical floor for step 3 onward is set by the distance. Light in optical fibre travels
at roughly two-thirds of its speed in vacuum, about 200,000 km per second.

<Claim label="inference">
Real measured round-trip times on this path are typically well above the theoretical floor,
because fibre does not run in straight lines and every router adds queueing and processing
delay. The floor is what matters for design: it is the part you cannot optimise away.
</Claim>

Now count the round trips before the application sees anything: DNS (assume it is cached, so
zero), TCP (one), TLS (one), request/response (one). That is three round trips at roughly
76 ms each, or about 230 ms — before your 40 ms of server work.

<Claim label="fact" source="rfc8446">
TLS 1.3 reduces the full handshake to one round trip, and offers a zero-round-trip resumption
mode for repeat connections. The specification also states that 0-RTT data does not carry
replay protection, which is why it must only be used for requests that are safe to repeat.
</Claim>

## Formal explanation

A request passes through a stack of layers, each of which solves a problem the layer below
does not.

- **<C id="dns" /> — naming.** Humans use names; the network routes to addresses. DNS is a
  distributed, aggressively cached lookup from one to the other. Its caching is the reason it
  is usually fast and the reason changes propagate slowly.
- **<C id="ip" /> — addressing and routing.** IP moves packets between addresses on a
  best-effort basis. Packets may be dropped, duplicated, or delivered out of order. IP
  promises nothing.
- **<C id="tcp" /> — a reliable stream.** TCP builds an ordered, reliable byte stream on top
  of that unreliability, using sequence numbers, acknowledgements and retransmission. This
  requires establishing shared state first: the handshake.
- **<C id="tls" /> — confidentiality and identity.** TLS negotiates keys and verifies the
  server's certificate before your data flows.
- **<C id="http" /> — semantics.** HTTP defines what a request *means*: which resource, which
  method, and what an intermediary is allowed to do with the response.

<C id="rtt">Round-trip time</C> is the currency of all of this. Every layer that requires
agreement before it can proceed costs at least one RTT, and RTT is bounded below by distance.

<Deeper title="Why the handshakes cannot simply be removed">

Each handshake exists to establish state that both ends need before they can safely proceed.

TCP's handshake synchronises sequence numbers so that both sides can detect loss and
reordering. Without it, an attacker could trivially inject data into a stream, and neither
side would know where a byte belonged.

TLS's handshake establishes keys and proves the server's identity. Skipping it means you have
no idea who you are talking to.

QUIC — the transport behind HTTP/3 — reduces this cost by combining the transport and
cryptographic handshakes into a single exchange rather than performing them in sequence. The
round trips did not become free; they were merged.

</Deeper>

## Scaling

A single request is a story about latency. Many requests turn it into a story about
resources — and the first resource to run out is rarely CPU.

<ScaleTable
  rows={[
    {
      scale: '1 request',
      behaviour: 'Latency is dominated by round trips. Server time is a rounding error.',
      firstToBreak: 'Nothing. This is the case everyone designs for.',
    },
    {
      scale: '100 concurrent',
      behaviour:
        'Each connection holds a socket and some memory. Connection setup cost starts to matter in aggregate.',
      firstToBreak: 'Nothing yet, but connection reuse is now worth real money.',
    },
    {
      scale: '10,000 concurrent',
      behaviour:
        'Open sockets, file descriptors and TLS session memory become significant. Handshake CPU cost is now visible.',
      firstToBreak:
        'File descriptor limits and TLS handshake CPU, long before request-handling CPU.',
    },
    {
      scale: '1,000,000 concurrent',
      behaviour:
        'Connections must be terminated close to users and multiplexed. A single origin cannot hold them.',
      firstToBreak:
        'The connection tier. This is why edge termination exists as a product category.',
    },
  ]}
/>

The important observation: at every scale above one, **the cost of establishing connections
grows faster than the cost of serving requests**. That is why keep-alive, connection pooling
and edge termination exist, and it is why they appear early in every serious architecture.

## Failure modes

  items={[

        'A dropped connection with no notification. TCP will retransmit patiently, and the client may wait far longer than any human will.',
      mitigation:

## Trade-offs

<TradeOff
  decision="Terminate TLS at the edge, close to users, rather than at the origin server"
  options={[
    'Terminate at the origin: one place to configure, full end-to-end encryption to your own machine',
    'Terminate at an edge network, then use a separate connection to the origin',
    'Terminate at the edge and re-encrypt to the origin',
  ]}
  why="Handshakes cost round trips, and round trips cost distance. Moving termination close to the user removes two long round trips from every new connection, while the edge holds a warm, reused connection to the origin."
  gain="Dramatically lower connection setup latency for distant users; handshake CPU moved off your origin; a natural place for caching, rate limiting and DDoS absorption."
  sacrifice="The edge sees your plaintext. You have added a third party to your trust boundary and a dependency you do not operate."
  failureModes={[
    'The edge provider has an outage and you have no direct path for users to reach the origin',
    'Certificate management is split across two systems and drifts',
    'The edge caches something user-specific because a header was misconfigured',
  ]}
  operationalBurden="Moderate: another system to configure and monitor, and a second place where routing rules live. Debugging now requires correlating logs across two providers."
  cost="Usually billed per request and per gigabyte egressed. Cheap at small scale, and a significant line item at large scale — often more than the origin servers."
  whenNot="When users are geographically concentrated near your origin, when regulatory constraints forbid a third party holding plaintext, or when your traffic is low enough that the added dependency is a bigger availability risk than the latency it saves."
/>

## In production

<RealWorld>

Connection reuse is not a micro-optimisation; it is one of the highest-leverage changes
available on a latency-sensitive path.

<Claim label="fact" source="rfc9112">
HTTP/1.1 makes persistent connections the default, so a connection is reused for subsequent
requests unless a party signals otherwise. This removes the setup cost from every request
after the first.
</Claim>

<Claim label="fact" source="rfc9113">
HTTP/2 goes further and multiplexes concurrent requests over a single connection, removing
the need to open several connections in parallel to achieve concurrency.
</Claim>

<Claim label="fact" source="rfc9000">
QUIC, which HTTP/3 runs over, provides per-stream reliability. A lost packet stalls only the
stream it belongs to, rather than every stream sharing the connection — the head-of-line
blocking problem that TCP-based multiplexing cannot avoid.
</Claim>

The practical consequence for a design discussion: if a service makes many small calls to
another service, the connection strategy is part of the design, not an implementation detail.

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'We will add a CDN to make the API faster.',
      why: 'A CDN removes distance for cacheable responses. An authenticated, per-user API response is generally not cacheable, so the CDN saves nothing on the response itself.',
      instead:
        'Say what the CDN actually buys here: terminating TLS near the user removes two long round trips from connection setup, and the connection to the origin is warm and reused. That is a real gain, and it is a different gain from caching.',
    },
    {
      mistake: 'Latency is a server problem, so we need bigger servers.',
      why: 'On a cold connection to a distant user, the server may account for well under a fifth of the total. Doubling server speed halves a small number.',
      instead:
        'Measure where the time goes before spending. Split the budget: DNS, connection setup, request transfer, server time, response transfer, rendering. Optimise the largest term.',
    },
    {
      mistake: 'We use HTTPS, so the connection is secure.',
      why: 'It is a claim about the transport, not about the system. It says nothing about who holds the plaintext at each hop, whether the certificate is verified, or whether an edge provider sits in the middle.',
      instead:
        'State where encryption starts and ends, and who is inside the trust boundary at each hop.',
    },
  ]}
