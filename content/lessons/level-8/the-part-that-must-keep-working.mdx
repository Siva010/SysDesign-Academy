## The problem

14:02. A configuration change is pushed — a routine one, adding a backend to a service. The
pipeline validates it, publishes it, and reports success.

14:02:30. The first load balancers poll for the new configuration. A bug in the generator emitted
an empty backend list. Each balancer receives it, applies it faithfully, and now has zero backends
for that service.

14:03:30. Every balancer has polled. Every one of them is returning errors. The entire service is
down.

Not one server failed. Every application instance is healthy, idle, and reachable, running the
same code it ran at 14:01. They are unreachable because the thing that tells traffic where to go
was told there is nowhere to go, and believed it.

Each balancer had a perfectly good backend list in memory thirty seconds earlier. It threw that
away because something newer arrived.

## Intuition

Every system has two parts, and most designs never name them separately.

The **data plane** does the work. It serves requests, moves packets, runs queries, delivers
messages. It is large, repetitive, and does the same thing millions of times a second.

The **control plane** decides what the data plane should do. Which backends exist. What the routing
rules are. Who has what quota. Which version is deployed, and to whom. It is small, complex, and
changes constantly.

Three asymmetries follow from that, and together they produce the whole lesson:

- **Change.** The control plane changes many times a day; the data plane changes rarely. Most
  outages are caused by change, so most outages originate in the control plane.
- **Complexity.** The control plane is where the interesting logic lives; the data plane is
  deliberately dull. That is the right direction — you want the complexity where the blast radius
  is smallest.
- **Scale.** The data plane handles the traffic; the control plane is sized for the rate of
  decisions, which is thousands of times smaller.

Put those together and the rule is not a preference, it is arithmetic: **the data plane must keep
working when the control plane is unavailable.** Not degrade gracefully, not fail politely — keep
serving, on the last configuration it knew was good, for as long as it takes.

That property has a name: **static stability**. A statically stable system's steady state does not
depend on anything continuing to make decisions.

## Concretely

<Example title="The same question, asked of three systems">

The question is always the same: *what does the data plane do when it cannot hear from the control
plane?*

**DNS.** A resolver holds a record until its TTL expires, then tries to refresh. If the
authoritative server is unreachable, resolution continues with what it has. The data plane —
answering queries — is decoupled from the control plane by design, and the TTL is an explicit
statement of how long that decoupling lasts. This is the oldest and most successful example of the
pattern in production.

**A load balancer polling for backends.** If it treats a failed fetch as an empty result, it fails
closed and the service dies. If it treats it as *keep what I have*, it fails static and the service
continues. Same code path, one line different, and the difference is a total outage.

**A feature flag evaluated by a network call.** When the call fails, does the feature default on or
off? Whichever you choose, it must be chosen. A library default decides it otherwise, and it will
decide it during an incident, in a direction nobody predicted.

There are only three possible answers to the question, and only one of them is ever chosen by
accident:

1. Keep the last known good state. **Static.**
2. Fall back to a compiled-in default. **Predictable, and possibly wrong.**
3. Stop. **Almost never intended, and the default in most implementations.**

</Example>

## Formal explanation

<C id="control-plane-vs-data-plane" /> is a split by *responsibility*, not by technology. The
control plane decides; the data plane executes. Any system can be described this way, and the
description is useful precisely because it identifies which half you are allowed to lose.

**The prohibition.** The data plane must not have a **synchronous dependency** on the control
plane. If serving a request requires a live call to the thing that holds configuration, then a
control-plane outage is a data-plane outage, and every property below is unavailable to you.

This is violated more often by accident than by decision. A per-request authorisation lookup, a
feature flag evaluated over the network, a quota check against a central service, a service
discovery call that is not cached — each is a small, reasonable-looking piece of code that quietly
makes a small complex system a hard dependency of a large simple one.

**Static stability.** The system continues in its current state without needing new instructions.
An instance that already has its configuration, its certificates, its routing table and its backend
list serves indefinitely. What it cannot do is *change* — no new deployments, no new backends, no
scaling — and that is exactly the right thing to lose, because those are the operations that were
going to be paused during the incident anyway.

**Distinguish no data from no answer.** The 14:02 outage happened because an empty response and a
failed response were handled identically, and both were treated as truth. They are different
propositions:

- *The control plane says there are zero backends.* Possible, and almost never what you meant.
- *The control plane did not answer.* Says nothing about backends at all.

Treat an empty configuration as suspicious by policy: reject a configuration that removes more than
some fraction of the current state, and require an explicit override for the case where you really
did mean to empty it. This costs one validation rule and prevents a whole family of total outages.

**Recovery is its own failure mode.** When the control plane returns, every data-plane instance
notices at once and asks it for the current state. A control plane sized for a steady trickle of
decisions receives its entire population simultaneously, and falls over again. Jittered polling and
a server-directed retry delay are not optional extras here — they are what makes the recovery
survivable.

<Callout kind="warn" title="The rollback path is part of the control plane">
The uncomfortable case: your configuration is broken, and the mechanism for fixing configuration is
the thing that is broken.

So the emergency path must not depend on the normal path. A previous configuration cached on each
instance and applied by a local command; a static fallback baked into the image; a break-glass
route that bypasses the pipeline entirely. Whichever you choose, it needs to be exercised, because
a rollback procedure that has never been run is a plan rather than a capability.
</Callout>

## Trade-offs

<TradeOff
  decision="Serve the last known good configuration indefinitely rather than expiring it"
  options={[
    'Fetch configuration per request from the control plane',
    'Cache with a hard expiry, and fail when it lapses',
    'Cache with a hard expiry, and keep serving the stale copy past it',
    'Compile configuration into the deployment artefact, so it changes only on release',
  ]}
  why="An expiry that lapses during a control-plane outage converts a survivable incident into a total one, at the exact moment refresh is impossible. Nothing about the configuration became wrong when the clock passed a threshold — only your confidence in it did, and confidence is not a reason to stop serving."
  gain="The data plane survives a control-plane outage of any duration. Recovery is a resynchronisation rather than a restart. The blast radius of the most change-prone, most complex component stops including the serving path."
  sacrifice="A stale configuration can persist without limit and without anyone noticing. A revoked permission, a disabled feature or a removed backend stays in effect until the next successful fetch, which may be much later than anyone assumes."
  failureModes={[
    'A permission revoked in the control plane still honoured by an instance that has not refreshed',
    'Drift, where instances run different configurations because they last fetched at different times',
    'A stale configuration that is never noticed because nothing alarms on its age',
  ]}
  operationalBurden="Low in code, real in discipline. It needs the applied version and its age exported as metrics, an alarm on both age and fleet-wide spread, and a local override path that is exercised rather than documented."
  cost="Negligible. This is one of the few reliability improvements that is close to free, which is a good reason to be suspicious of designs that have not taken it."
  whenNot="When the configuration carries something that must be revocable within a bounded time — an access grant, a compromised credential, a legal hold. There, unbounded staleness is the failure rather than the protection, and the right shape is a bounded window with an explicit, decided behaviour when it lapses. Note that this is an argument for keeping revocation *out* of the same channel as routing configuration, so that one can fail static while the other fails closed."
/>

## In production

<RealWorld>

<Claim label="convention" source="aws-builders-library">
Static stability is described as a design goal in which a system continues to operate correctly
without needing to make changes during a failure, on the grounds that the mechanisms which make
changes are themselves likely to be impaired at that moment.
</Claim>

<Claim label="fact" source="rfc1035">
DNS records carry a time to live, and resolvers answer from cache for that duration without
contacting an authoritative server. Resolution therefore continues while the authoritative side is
unreachable, which is a decoupling of serving from control expressed as a protocol field.
</Claim>

<Claim label="convention" source="sre-book">
A significant share of production incidents originate in change — configuration pushes and
releases — rather than in hardware or organic load, which is why limiting the blast radius of
change is treated as a primary reliability practice.
</Claim>

<Claim label="convention" source="release-it">
A component that every request depends on transmits its own failures to everything downstream, so
shared dependencies on the request path deserve scrutiny in proportion to how many callers they
have rather than to how often they fail.
</Claim>

<Claim label="recommendation" source="aws-well-architected">
Workloads should be designed so that the data plane can continue to operate when the control plane
is unavailable, and recovery mechanisms should avoid depending on the components most likely to be
impaired during the event they exist to recover from.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Evaluating a feature flag with a network call on the request path.',
      why: 'It puts a small, frequently changed service into the critical path of every request in the product. Its latency becomes your latency and its outage becomes your outage, in exchange for a freshness nobody asked for.',
      instead:
        'Fetch the flag set in the background, evaluate locally, and define what each flag does when the set is stale or missing. The default for an unreachable flag service should be a decision recorded next to the flag, not a library default.',
    },
    {
      mistake: 'Treating an empty response as an authoritative answer.',
      why: 'Zero backends, zero rules or zero tenants is almost always a bug rather than an instruction, and applying it faithfully turns a producer-side defect into a consumer-side total outage within one poll interval.',
      instead:
        'Validate the shape of the change, not only its syntax. Reject anything that removes most of the current state unless it carries an explicit override, and log loudly when you do.',
    },
    {
      mistake: 'Assuming the control plane is available during an incident.',
      why: 'It is the most complex and most frequently changed part of the system, so it is disproportionately likely to be involved in the incident. Building recovery procedures on top of it means the tools are unavailable exactly when they are needed.',
      instead:
        'Make every emergency path independent of the normal path, and exercise it on a schedule. A procedure that has only ever been written down is a hypothesis about your own system.',
    },
  ]}
