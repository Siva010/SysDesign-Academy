## The problem

Two databases. Same hardware, same data, same schema.

On database A, writes sustain 8,000 per second and reads are consistently 0.4 ms. On database
B, writes sustain 60,000 per second, reads average 0.9 ms, and every few hours the p99 read
latency jumps to 40 ms for several minutes.

Neither is broken. Neither is misconfigured. They made different choices about one thing: what
to do when you change a byte that is already on disk.

## Intuition

You keep a sorted address book.

**Update in place.** When someone moves, you find their entry and rewrite it. The book stays
perfectly sorted, so lookups are always fast. But rewriting means finding the page, erasing,
writing — and if the entry grows, shuffling everything after it. Changes are slow and land in
scattered places.

**Append and merge later.** You never rewrite. New information goes on a fresh page at the
back: &ldquo;Alex moved to 12 Oak Street&rdquo;. Writing is trivial — always the same place,
always sequential. But now a lookup must check the back pages before trusting the main book,
and the more back pages accumulate, the slower lookups get. So periodically you sit down and
merge the loose pages into the book properly. That merge is expensive, and it happens while
people are still asking you for addresses.

The first is a <C id="btree">B-tree</C>. The second is an
<C id="lsm-tree">LSM tree</C>. Everything else in this lesson is consequences.

## Concretely

<Example title="What one row update costs, in each design">

**B-tree.** Locate the leaf page (a few reads, usually cached), modify it in memory, write the
change to the WAL so it is durable, and eventually write the page back to its home location.
The page write is at a fixed position determined by the key — which means it is a random write.
If any index covers the changed column, repeat for each index.

**LSM tree.** Append to the WAL, insert into an in-memory sorted structure, and return. That
is the whole write. Later, when the in-memory structure is full, flush it to disk as an
immutable sorted file. Later still, merge those files together.

The LSM write path touches disk sequentially and never seeks. That is why write throughput can
be an order of magnitude higher.

The cost arrives on the read path and in the background. A read may have to check the in-memory
structure, then several on-disk files, because the key could be in any of them. And compaction
— the merging — competes with your live traffic for disk bandwidth and CPU, which is what
produces those periodic p99 spikes.

</Example>

## Formal explanation

**B-tree.** A balanced tree of fixed-size pages, sorted by key. Lookups descend from the root:
a handful of page reads, with the upper levels almost always cached. Depth grows extremely
slowly with data size, so lookup cost is nearly constant. Range scans walk the leaves in order.
Writes modify pages in place, which produces random I/O and requires the
<C id="wal">write-ahead log</C> for crash safety.

**LSM tree.** Writes accumulate in a sorted in-memory structure. When it fills, it is flushed
to disk as an immutable <C id="sstable" /> — a sorted file that is never modified again.
Because files are immutable and sorted, merging them is a linear scan.
<C id="compaction" /> does that merging, discarding superseded values and reclaiming space.

Three amplification factors describe the trade:

- **<C id="write-amplification" />**: one logical write becomes several physical writes.
  B-trees amplify through page writes and index maintenance; LSM trees amplify through repeated
  rewriting during compaction.
- **<C id="read-amplification" />**: one logical read touches several structures. Minimal in a
  B-tree, real in an LSM tree, mitigated by <C id="bloom-filter">Bloom filters</C> that let the
  engine skip files that definitely do not contain the key.
- **Space amplification**: how much more disk than the logical data. LSM trees hold superseded
  versions until compaction removes them.

<Callout kind="info" title="This is not a database-brand decision">
Several databases offer both, and the right answer can differ per table. The question is
always about the workload: read-heavy with strict latency, or write-heavy with tolerance for
tail variance.
</Callout>

<Deeper title="Why compaction shows up in your p99">

Compaction reads several SSTables and writes a merged one. That is a large amount of sequential
I/O and CPU, and it happens on the same machine serving your queries.

The consequences are characteristic and worth recognising in a graph:

- **Periodic latency spikes** with no correlation to traffic. Reads compete with compaction for
  disk bandwidth.
- **A write-stall cliff.** If writes arrive faster than compaction can keep up, the number of
  files grows, read amplification worsens, and eventually the engine throttles writes
  deliberately to let compaction catch up. Throughput does not degrade gently here; it steps
  down.
- **Disk headroom is not optional.** A merge needs room for both the inputs and the output. A
  full disk on an LSM store can be unrecoverable without adding capacity, because the operation
  that would free space needs space to run.

<Claim label="fact" source="cassandra-docs">
Cassandra offers multiple compaction strategies, and the choice is workload-dependent:
size-tiered favours write throughput, levelled favours read latency and space efficiency at
the cost of more compaction I/O.
</Claim>

The general lesson generalises beyond LSM trees: **background maintenance work is part of your
latency profile.** Vacuum in a B-tree engine, index rebuilds, garbage collection in your
runtime — all of them show up in the tail, and all of them are invisible if you only monitor
averages.

</Deeper>

## Trade-offs

<TradeOff
  decision="Choose an LSM-based store for a high-ingest workload"
  options={[
    'B-tree engine: predictable reads, in-place updates',
    'LSM engine: high write throughput, deferred merge cost',
    'B-tree engine with the write path buffered by a queue and batched inserts',
  ]}
  why="If sustained write throughput is the binding constraint, sequential appends beat random page updates by roughly an order of magnitude, and no amount of tuning closes that gap for a B-tree."
  gain="Much higher ingest on the same hardware. Better compression, because immutable sorted files compress well. Writes do not seek, so cheaper storage remains viable."
  sacrifice="Read latency becomes variable rather than flat. Compaction consumes disk bandwidth and CPU continuously, and it shows up in your tail latency. You need substantial free disk headroom."
  failureModes={[
    'Compaction falling behind, causing read amplification and then write throttling',
    'Disk exhaustion during a merge, which is hard to recover from',
    'Tail latency spikes uncorrelated with traffic, which are hard to explain to stakeholders',
  ]}
  operationalBurden="Higher than a B-tree engine. Compaction strategy, disk headroom, and file-count monitoring are ongoing concerns rather than one-time settings."
  cost="Often cheaper per unit of ingest, because the write pattern suits inexpensive storage and the data compresses well. The saving is partly offset by needing headroom you cannot use."
  whenNot="When reads dominate and latency consistency matters more than ingest — a user-facing product catalogue, a permissions store — the compaction tail is a cost with no corresponding benefit. Also when the workload has heavy point updates to existing rows rather than appends, since LSM engines handle overwrite-heavy workloads less gracefully than their write throughput suggests."
/>

## In production

<RealWorld>

<Claim label="fact" source="database-internals">
B-trees update pages in place, producing random writes; LSM trees buffer writes and flush
immutable sorted files, producing sequential writes at the cost of read amplification and
ongoing compaction.
</Claim>

<Claim label="fact" source="bigtable">
Bigtable's design uses in-memory tables flushed to immutable sorted files on a distributed file
system, with periodic compaction — the structure that later became the standard LSM
architecture for wide-column stores.
</Claim>

<Claim label="fact" source="postgres-docs">
PostgreSQL's default index type is a B-tree, and its MVCC implementation requires periodic
cleanup of dead row versions. A long-running transaction prevents that cleanup, which is a
common cause of unexpected table growth.
</Claim>

<Claim label="recommendation">
Judge a storage engine on your workload with a dataset larger than memory, run for long enough
that background maintenance reaches steady state. Short benchmarks on small data reliably
mislead in both directions.
</Claim>

</RealWorld>
