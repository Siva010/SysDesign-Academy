## The problem

A property listings site stores everything in one relational database, which is the correct
default and works for two years.

Then three complaints arrive in the same month, from three different people, and nobody connects
them.

The nightly backup now takes six hours and overlaps the morning traffic. The
&ldquo;properties near me&rdquo; search times out for anyone in a city. And a surveyor on a
mobile connection, annotating a 40 MB floor plan on site, waits four minutes to upload a change of
two kilobytes.

Three unrelated symptoms. One cause: the storage and the index were built to answer questions
about rows identified by keys, and none of this data is a row identified by a key.

## Intuition

A B-tree is a sorted list with a fast way to find a position in it. That means it answers exactly
two questions well:

- **What is the row with this key?**
- **What are the rows between these two keys?**

Almost everything a relational database does quickly is one of those two wearing different
clothes. A join is repeated lookups. An index scan is a range. A sort that uses an index is a walk.

Three kinds of data cannot be expressed as either question, and no amount of indexing changes
that:

- **Data with two independent dimensions.** Sorting by one discards the other. There is no
  ordering of a map that puts everything nearby next to each other, because a line has one
  direction and a map has two.
- **Data too large to be a value.** The index is irrelevant here. Whatever you do, the bytes have
  to move, and they have to move through everything that touches the row — backups, replication,
  the page cache.
- **Data where the question is &ldquo;what changed?&rdquo;** A key identifies a version. It does
  not tell you the difference between two versions, and computing that difference by comparing two
  whole objects is exactly the work you were trying to avoid.

The rest of this lesson is one structure for each.

## Concretely

<Example title="The three complaints, with their numbers">

**The slow backup.** Floor plans are stored in a column on the listings table, averaging 40 MB.
Ten thousand listings is 400 GB of blobs sitting in a table whose actual queryable data is about
2 GB. Every backup copies all 400 GB. Every replica ships all 400 GB. Worst of all, the page cache
is filled with bytes no query has ever looked at, so the 2 GB that *is* queried keeps being
evicted.

**The slow proximity search.** A 5 km box around a point in a city spans roughly 0.045 degrees of
latitude and 0.06 of longitude. There is an index on each. The latitude index narrows the search
to a band 5 km tall — stretching from the Atlantic to the Urals, about 2 million listings. The
longitude index narrows to a strip 5 km wide from pole to pole, about 1.5 million. The planner
picks one, reads millions of rows, and discards all but the two hundred that are in both.

**The slow upload.** The surveyor's annotation changed 2 KB of a 40 MB file. The client has no way
to say so, because the interface takes a file, so it sends 40 MB. On a mobile connection at
1.5 Mb/s that is about four minutes for a change that would fit in a text message.

</Example>

## Formal explanation

### Where the bytes live

<C id="block-storage" /> is a virtual disk attached to one machine. It presents blocks, a
filesystem sits on top, and you can modify any byte in place. Latency is low, semantics are
familiar, and it inherits two properties from being a disk: it is **tied to one machine's failure
domain**, and its capacity is **decided in advance**.

Object storage is the opposite trade: whole immutable blobs addressed by key over HTTP,
effectively unlimited, replicated across failure domains, with higher first-byte latency and **no
partial update**. Changing one byte means writing the whole object again.

The decision has one question in it: **does anything need to modify part of this in place?** A
database's own files, yes — that is what block storage is for. A user's uploaded floor plan, no. It
is written once, read many times, and replaced wholesale when it changes.

For the second case the payoff is not primarily cost. It is that capacity planning disappears, the
failure domain disappears, and the bytes stop travelling through your application at all: the
client uploads directly and downloads directly, and the database holds a key.

### Two dimensions into one key

A <C id="geospatial-index" /> exists because the problem in the example is not fixable by adding
indexes. Two separate B-trees each narrow one dimension, and the planner must intersect two very
wide ranges.

Two families of answer:

**A spatial tree.** An R-tree, or PostgreSQL's GiST framework, indexes bounding boxes directly and
handles containment and overlap queries properly. This is the right answer for data whose write
rate is ordinary, which is nearly all spatial data — property listings, shop locations, delivery
zones.

**A cell or curve scheme.** Interleave the two coordinates into a single ordered value — a
geohash, a quadtree path, an S2 cell id — so that points near each other in space are usually near
each other in the ordering. Proximity becomes a range scan on one ordinary index, and membership
becomes a set keyed by cell, which is why this is what a system with a very high write rate
reaches for.

<Callout kind="info" title="Why the word is usually">
No mapping from two dimensions to one preserves proximity perfectly. Any curve that covers a plane
must, somewhere, jump — two points on opposite sides of a cell boundary are adjacent in space and
distant in the ordering.

That is not a defect of a particular scheme; it is a property of flattening a plane onto a line.
It is also why a proximity search reads **several cells** rather than one range: the neighbours of
a cell have to be visited explicitly, because the ordering will not deliver them.
</Callout>

### What changed, rather than what it is

<C id="chunking" /> splits a large object into pieces addressed by the hash of their contents, so a
client and a server can agree on what to transfer by exchanging hashes instead of bytes.

The mechanism that makes it work is the choice of boundaries. Cut at fixed 4 MB offsets and insert
one byte at the front: every boundary shifts, every chunk hash changes, nothing matches, and the
whole object is re-sent. Cut where a rolling hash of the content matches a pattern, and the
boundaries are properties of the bytes rather than of the offsets — so an insertion changes only
the chunks around it and everything after re-aligns on its own.

Three consequences follow, and the third is a gift:

- **Transfer becomes proportional to the change**, not to the object. The 40 MB upload becomes
  one 4 MB chunk plus a list of hashes.
- **Identical chunks are stored once.** Deduplication is free, because identical content produces
  an identical address.
- **Integrity comes with it.** A content address is a checksum you were already storing. A chunk
  that does not hash to its own name is corrupt, and you find out on read rather than on restore.

The cost lands on the client: computing hashes means reading the file, so a 40 MB object is read
in full every time it changes. Cache the chunk list against path, size and modification time, or a
laptop's fan becomes part of your architecture.

## Trade-offs

<TradeOff
  decision="Store large objects outside the database, with the row holding only a key"
  options={[
    'A binary column in the row: one store, one transaction, one backup',
    'A separate table for blobs in the same database',
    'Object storage, with the row holding a key',
    'A filesystem on block storage, with the row holding a path',
  ]}
  why="Bytes in a row are carried by everything that touches the row — backups, replication, the page cache — even though no query ever reads them. Moving them out is the single largest structural improvement available to most systems that store user uploads."
  gain="Backups and replicas shrink to the size of the queryable data. The page cache holds only data queries read. Capacity planning for uploads disappears. Clients transfer directly, so bytes never occupy an application worker, and delivery can go through a CDN."
  sacrifice="Two stores that can disagree. The write is no longer atomic, so a crash between the upload and the metadata write leaves an orphan. Deleting a listing no longer deletes its bytes unless something does that explicitly."
  failureModes={[
    'Orphaned objects from abandoned uploads, accumulating silently',
    'Metadata written before the bytes exist, producing a listing whose file will not download',
    'Deletes that remove the row and leave the object, which is a compliance problem as well as a cost one',
  ]}
  operationalBurden="Moderate. A garbage collector with a grace period, a lifecycle policy, and a deletion path that covers both stores. None of it is hard; all of it must actually be written."
  cost="Object storage is far cheaper per byte than database storage, and the saving on backup and replica volume is usually larger than the saving on the bytes themselves."
  whenNot="When the objects are small — a few kilobytes of JSON, a thumbnail — the second store costs more in complexity than the bytes cost in the row. When the write must be atomic with the row and you cannot tolerate an orphan window even briefly, keeping them together is defensible, though ordering the writes bytes-first usually removes the need. And when the object must be modified in place rather than replaced, object storage cannot do it and block storage is the answer."
/>

## In production

<RealWorld>

<Claim label="fact" source="postgres-docs">
PostgreSQL stores oversized field values out of line in a separate area, transparently, because a
row must fit within a page. The values are still part of the table for backup and replication
purposes.
</Claim>

<Claim label="fact" source="postgres-docs">
GiST is an index framework for data types that lack a natural linear ordering, including geometric
types, supporting containment and overlap operators that B-tree operators cannot express.
</Claim>

<Claim label="fact" source="database-internals">
Multi-dimensional data is commonly indexed by mapping several dimensions onto a single ordered
value using a space-filling curve, so that a proximity query becomes a range scan. The mapping
cannot preserve proximity exactly, so neighbouring regions must be queried explicitly.
</Claim>

<Claim label="fact" source="redis-docs">
Redis implements geospatial queries on sorted sets by encoding a coordinate pair into a single
score, and provides radius queries over that encoding.
</Claim>

<Claim label="recommendation" source="aws-well-architected">
Matching storage type to access pattern is a documented practice: block storage for data requiring
in-place modification and low-latency access from one instance, object storage for whole immutable
objects requiring durability and scale.
</Claim>

<Claim label="convention" source="dropbox-tech">
Published engineering writing on file synchronisation describes splitting files into
content-addressed blocks so that transfers are proportional to the change rather than to the file,
and identical blocks are stored once.
</Claim>

<Claim label="fact" source="ddia">
Content-addressed immutable storage simplifies caching and replication, because an object
identified by the hash of its contents cannot become stale and writing it twice is
indistinguishable from writing it once.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Indexing latitude and longitude separately.',
      why: 'Each index narrows one dimension only, so the planner must intersect two ranges that are each enormous. The query reads millions of rows to return a few hundred, and it looks like it should work, which is why it survives review.',
      instead:
        'Use a spatial index, or derive one ordered key from both coordinates. Then read the query plan to confirm it is being used, because adding the index is not the same as the planner choosing it.',
    },
    {
      mistake: 'Keeping user uploads in a database column because it keeps the write atomic.',
      why: 'Atomicity is real and it is bought by making every backup, every replica and the page cache carry bytes no query reads. The cost is paid continuously; the benefit applies to a window of a few seconds around the upload.',
      instead:
        'Write the bytes first, then the metadata. An orphaned object is inert and collectable; metadata pointing at bytes that do not exist is data loss as far as the user is concerned.',
    },
    {
      mistake: 'Chunking at fixed offsets.',
      why: 'It is the obvious implementation and it fails on the most common edit there is. Anything inserted rather than overwritten shifts every subsequent boundary, so no chunk matches and the entire object is re-sent.',
      instead:
        'Choose boundaries with a rolling hash over the content, so they move with the bytes. This is the whole reason content-defined chunking exists, and it is not an optimisation over the fixed version — it is the difference between working and not.',
    },
  ]}
