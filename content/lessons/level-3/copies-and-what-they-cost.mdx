## The problem

You add a read replica. Read capacity doubles. Everyone is pleased.

Then the support tickets start, and they are all variations of one complaint:

- A user updates their profile, the page reloads, and the old name is there.
- A comment is posted, disappears on refresh, and reappears a moment later.
- A dashboard shows a total that does not match the sum of the rows beneath it.

Nothing is broken. Each replica is faithfully applying the writes it has received. The problem
is that &ldquo;has received&rdquo; is a different point in time for each of them, and your
application forgot that.

## Intuition

Replication is photocopying, continuously.

The original is the leader. Every change is written there, and a stream of changes flows to
each copy. Copies are useful: they survive the original burning down, they let many people read
at once, and one can sit in another country so local readers do not wait.

But a copy is always at least slightly behind. The question is only how far, and what happens
in that window.

Two decisions define everything:

**Where can writes happen?** One place (simple, and that place is your write ceiling and your
failure point), several places (available and fast everywhere, and now two people can change
the same thing in two places), or no fixed place at all (quorum-based, flexible, and
complicated).

**Does a write wait for its copies?** If yes, you pay latency on every write and you fail when
a replica is unreachable. If no, writes are fast and a failover can lose the ones that had not
arrived.

There is no configuration in which you avoid choosing.

## Concretely

<Example title="Where the lag actually shows up">

A user updates their display name. The write goes to the leader and returns. The page reloads
and the read is routed to a replica that is 80 ms behind. The old name appears.

Eighty milliseconds sounds harmless. It is not, because a page reload after a form submission
lands inside that window almost every time.

The general shape: **any read that closely follows a write by the same user will land in the
lag window.** This is not an edge case; it is the most common user interaction there is.

Three session guarantees fix specific symptoms:

- **<C id="read-your-writes" />** — a user always sees their own updates. Route that user's
  reads to the leader for a short period after they write, or track the write position and
  require a replica to have caught up to it.
- **<C id="monotonic-reads" />** — time never appears to run backwards for one user. Pin a user
  to one replica so they cannot bounce between a fresher and a staler copy.
- **Consistent prefix** — a user never sees an effect before its cause, which matters when
  reading across partitions replicated independently.

Note what these have in common: they are all *per-user* guarantees. They make eventual
consistency feel correct without paying for global consistency, and that is usually the right
trade.

</Example>

## Formal explanation

<C id="leader-follower" /> replication designates one node to accept writes and stream them to
followers, usually by shipping the <C id="wal">write-ahead log</C>. It is the default in most
relational systems because it is simple to reason about: there is one authoritative order of
writes.

<C id="sync-vs-async-replication">Synchronous or asynchronous</C> is the load-bearing choice:

- **Synchronous** — the leader waits for at least one follower to acknowledge before
  confirming the commit. No committed write is lost on failover. Write latency now includes a
  round trip to the follower, and if the follower is unreachable, writes stall.
- **Asynchronous** — the leader confirms immediately. Fast, and a failover can lose writes that
  had not yet been shipped. That loss window is your <C id="rpo">RPO</C>.
- **Semi-synchronous** — wait for one follower, not all. The usual compromise: bounded loss,
  bounded latency cost.

<C id="replication-lag" /> is how far behind a follower is. It is not constant. It grows under
write bursts, during long-running queries on the follower, and after any network hiccup — which
means it is largest precisely when the system is busiest.

<Callout kind="warn" title="Replicas are not backups">
Replication faithfully copies your DELETE to every replica in milliseconds. It protects against
a machine failing, not against a bad migration, a buggy deploy, or someone running an UPDATE
without a WHERE clause. Only an independent copy that is not continuously synchronised does
that, and only if you have tested restoring it.
</Callout>

<Deeper title="Read replicas do not scale writes, and each one costs the leader">

The arithmetic is worth being explicit about, because &ldquo;add a replica&rdquo; is offered
as a general scaling answer far more often than it should be.

Every replica applies **every** write. If the leader sustains 5,000 writes per second, each
replica must also sustain 5,000 writes per second just to keep up. Adding replicas therefore
does not increase write capacity at all — and in a single-threaded replication implementation,
a replica can fall behind a leader that is using many cores to accept writes in parallel.

Each replica also adds load to the leader: another stream to ship, another connection to
maintain.

So the honest statement is: **read replicas scale reads, at the cost of staleness, and they
make the write ceiling very slightly worse.** When writes are the constraint, replicas are not
the answer — partitioning is.

</Deeper>

## Trade-offs

<TradeOff
  decision="Serve most reads from asynchronous replicas, with read-your-writes routing for recent writers"
  options={[
    'All reads from the leader: consistent, and the leader is the ceiling',
    'All reads from async replicas: maximum capacity, visible staleness',
    'Async replicas with per-user routing to the leader after a write',
    'Synchronous replication so replicas are never behind',
  ]}
  why="Most reads have no relationship to a recent write by the same user, and for those, a few tens of milliseconds of staleness is invisible. The small fraction that do follow a write are exactly the ones users notice, and those can be routed specially."
  gain="Read capacity scales with replica count, while the anomaly users actually notice is eliminated. The leader is freed to spend its capacity on writes."
  sacrifice="Routing complexity: something must track who wrote recently, and that state has to live somewhere. Other users still see stale data, which is usually fine and occasionally is not."
  failureModes={[
    'The routing window is too short and the replica has not caught up',
    'Reads for one user land on different replicas, so values appear to move backwards',
    'A badly lagging replica stays in the read pool because lag is not monitored',
  ]}
  operationalBurden="Moderate. Lag must be monitored and used for routing decisions. The routing state — who wrote recently — is a small piece of shared state with its own failure mode."
  cost="One machine per replica, plus its storage. Cheap relative to the read capacity gained, and the cheapest read scaling available before partitioning."
  whenNot="When every read must reflect the latest write — balances, permissions, inventory at point of sale — routing to a replica is a correctness problem rather than a performance trade. ## In production

<RealWorld>

<Claim label="fact" source="postgres-docs">
PostgreSQL supports streaming replication with synchronous, asynchronous and quorum-based
commit modes, and exposes replication lag so applications and routers can make decisions based
on it.
</Claim>

<Claim label="fact" source="mysql-docs">
MySQL replication is asynchronous by default, with semi-synchronous available. Replication
delay can grow when a replica applies changes less parallel than the source produced them.
</Claim>

<Claim label="convention" source="sre-book">
RPO and RTO should be stated explicitly rather than inherited from defaults. Asynchronous
replication implies a non-zero RPO, and the size of that window is a business decision that
belongs in the design, not in the configuration file.
</Claim>

<Claim label="recommendation">
Test the failover, on a schedule, in production-like conditions. A failover path that has never
been exercised is a hypothesis, and it will be tested for the first time during an incident.
</Claim>

</RealWorld>

## Common mistakes

  items={[
    {
