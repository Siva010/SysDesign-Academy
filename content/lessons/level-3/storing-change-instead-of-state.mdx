## The problem

A customer says their account balance is wrong. It reads 47.

The support engineer opens the row. It says 47. There is a `updated_at` from Tuesday and nothing
else. What did it used to be? What changed it? Was it one adjustment or nine? Did a retry apply a
credit twice?

Nobody can say, because the answer was overwritten. The column holds the current value and the
system was never asked to remember anything else. So the investigation becomes a search through
application logs, which were sampled, rotated after fourteen days, and never designed to answer
this question.

Meanwhile a second team wants a report on how balances moved through the quarter. That data does
not exist. It never existed. It was destroyed continuously, one `UPDATE` at a time, by a system
working exactly as designed.

## Intuition

There are two ways to record what a bank account is doing.

**Write down the balance and change it.** The current value is instantly available and one row per
account. Every change replaces the previous truth.

**Write down each transaction and add them up.** The balance is derived. Every change is a new
line and nothing is ever removed.

A real bank does the second, and not for technical reasons. It does it because &ldquo;how did we
get here&rdquo; is a question someone will certainly ask, and a system that stores only the answer
cannot answer it.

The trade is genuine in both directions:

- Storing state is cheap to read, cheap to store, and forgets.
- Storing changes remembers everything, costs more to read, and grows forever.

And the asymmetry that decides it: **you can always compute the state from the changes, and you can
never recover the changes from the state.** Choosing to store state is choosing to destroy
information permanently, which is fine when nobody will want it and catastrophic when they do —
and you find out which several years later.

## Concretely

<Example title="The same account, two designs">

**State.** `accounts(id, balance)`. Reading is one lookup. The question &ldquo;why 47?&rdquo; has
no answer inside the system. A duplicate credit from a retried request is invisible: the balance is
simply 10 higher than it should be, and there is no record distinguishing that from a legitimate
credit.

**Changes.** `entries(account_id, amount, reason, source_id, occurred_at)`. The balance is a sum.
Every question about history is a query. The duplicate credit is *visible* — two entries with the
same `source_id` — and it is also *preventable*, because a unique constraint on `source_id` makes
the double application impossible rather than merely detectable.

Then the costs arrive.

Reading a balance is now a sum over every entry ever written. For an account with 400,000 entries
that is unacceptable, so you add a **snapshot**: a stored balance as of entry 399,000, plus the
entries since. The snapshot is a cache of a fold, and it must be rebuildable, because it will be
wrong at some point.

And correcting a mistake changes shape entirely. You cannot edit an entry, because entries are what
happened. You append a **correcting entry**, and the wrong value stays in history with its
correction next to it. Accountants have done this for centuries and call it a reversal. Engineers
usually find it uncomfortable the first time, because &ldquo;just fix the data&rdquo; is no longer
available.

</Example>

## Formal explanation

<C id="immutability" /> is the shared foundation. Append-only data can be cached without
invalidation, replicated without conflict, and read without locking, because nothing it says will
ever change. The costs are that storage grows monotonically and that nothing can be corrected in
place.

<C id="event-sourcing" /> stores the sequence of changes as the source of truth and derives current
state by folding them. What it buys:

- **A complete history**, by construction rather than by remembering to log.
- **New views over old data.** A question invented next year can be answered over events already
  stored, which is impossible when only current state was kept.
- **Debugging by replay.** Reproduce the exact state at the moment of a bug.
- **An audit trail** that cannot silently disagree with the data, because it *is* the data.

What it costs, and none of these are small:

- **Reads become folds**, so snapshots are mandatory at any real volume, and snapshots are derived
  data that must be rebuildable.
- **Event schemas are permanent.** A five-year-old event must still be readable by today's code,
  so every schema change is additive and every old shape is supported forever.
- **Correction is by compensation**, never by editing. Operationally this is the largest change,
  and it is cultural as much as technical.
- **Deletion becomes hard.** An immutable log and a legal obligation to erase personal data are in
  direct conflict.

<Callout kind="warn" title="Erasure and immutability have to be reconciled at design time">
&ldquo;Delete everything you hold about this person&rdquo; cannot be satisfied by appending an
event that says they asked. Two workable approaches, both of which must be chosen before the first
event is written:

- **Keep personal data out of the log.** Events carry a reference; the personal data lives in a
  mutable store that can be deleted. The log keeps the shape of what happened without the identity.
- **Encrypt per subject and delete the key.** The events remain, and become permanently
  unreadable. Sometimes called crypto-shredding, and it requires a key management story that exists
  from day one.

Retrofitting either onto a log that already contains names and addresses means rewriting the log,
which is exactly the operation the design said was impossible.
</Callout>

<C id="cqrs" /> separates the model used for writes from the models used for reads. The write model
enforces invariants; read models are shaped for particular queries and derived asynchronously.

Two things are routinely misunderstood:

**It is independent of event sourcing.** Either can be adopted without the other, and adopting both
at once is two large increases in complexity taken simultaneously. They are frequently discussed
together because event sourcing makes read models natural to build, not because either requires
the other.

**It is applied per query, not per system.** A specific query poorly served by the write model gets
a read model. Applying it globally makes every read eventually consistent, including the ones that
must not be — a permission check, a balance at the point of payment.

<C id="denormalisation" /> is what a read model is made of: data pre-joined and duplicated so a
query becomes a lookup. And here is the distinction worth carrying away:

**Denormalisation in a derived read model is safe. Denormalisation in a hand-maintained table is
not.** Both duplicate data and both can drift. The difference is that a derived model has an
authority to be rebuilt from, so drift is a temporary condition with a known remedy. A denormalised
table maintained by application code has no authority, so drift is permanent and each instance
needs a bespoke repair. The duplication is identical; the recoverability is not, and that is the
whole difference between a technique and a liability.

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Reads slow down as entities age',
      symptom: 'Latency grows steadily over months and is worst for the oldest, most valuable accounts.',
      cause: 'Every read folds the entire event history and no snapshots exist.',
      mitigation: 'Snapshot at intervals and read from the snapshot plus subsequent events. Treat snapshots as a rebuildable cache, never as an authority.',
    },
    {
      what: 'An old event can no longer be read',
      symptom: 'A replay or rebuild fails on data written years ago.',
      cause: 'The event schema changed in a non-additive way, or serialised objects were stored whose classes have since been refactored.',
      mitigation: 'Additive changes only, versioned events, upcasting functions from old shapes to new. Store data, never serialised object graphs.',
    },
    {
      what: 'Nobody can fix the data',
      symptom: 'A bad batch of events is in the log and there is no way to remove them.',
      cause: 'The log is immutable by design, and the team expected to be able to correct it in place.',
      mitigation: 'Design the correction path deliberately: compensating events, and projections that understand them. Rehearse it before you need it.',
    },
    {
      what: 'Read model drift',
      symptom: 'A derived view disagrees with the log and nobody knows for how long.',
      cause: 'A projection bug, a dropped event, or a schema change applied to one side only.',
      mitigation: 'Reconcile periodically by comparing counts and checksums, and keep a tested rebuild. A read model that cannot be rebuilt has become an authority by accident.',
    },
    {
      what: 'Erasure obligation cannot be met',
      symptom: 'A legal request to delete personal data arrives and the architecture makes it impossible.',
      cause: 'Personal data was written into an immutable log with no scheme for removing it.',
      mitigation: 'Keep personal data out of events, or encrypt per subject so the key can be destroyed. Both are design-time decisions.',
    },
    {
      what: 'Both patterns adopted at once, for neither reason',
      symptom: 'A small team is operating an event store, several projections and a rebuild pipeline for a system whose queries one database served well.',
      cause: 'The two patterns were treated as one modern architecture rather than as two independent decisions.',
      mitigation: 'Adopt each in response to a specific measured problem. One at a time, with the problem named first.',

## Trade-offs

<TradeOff
  decision="Store the sequence of changes as the source of truth instead of current state"
  options={[
    'Current state only, updated in place',
    'Current state plus an append-only audit table maintained alongside it',
    'Event sourcing: events are the truth, state is derived',
    'Current state plus change data capture, so history is derived from the database log',
  ]}
  why="History, replay and audit stop being features to build and become properties of the storage model. Any question about the past becomes answerable, including questions nobody has thought of yet."
  gain="Complete history by construction. New derived views over old data. Debugging by replay. An audit trail that cannot disagree with the data because it is the data. Duplicate operations become detectable and preventable by natural key."
  sacrifice="Reads become folds, requiring snapshots. Event schemas must be supported forever. Corrections are appended rather than applied. Deletion becomes a design problem rather than a statement. Storage grows without bound."
  failureModes={[
    'Fold latency growing with entity age',
    'Old event versions becoming unreadable',
    'Read models drifting with no reconciliation',
    'An erasure obligation the architecture cannot satisfy',
  ]}
  operationalBurden="High. Snapshot management, projection rebuilds, event schema governance, and a team that must be comfortable correcting data by appending rather than editing — which is a habit change, not a tooling change."
  cost="Storage grows monotonically, and compute is spent folding and projecting. Both are usually affordable; the expensive part is the engineering discipline the model requires indefinitely."
  whenNot="When history genuinely does not matter — a cache, a session, a derived aggregate — the audit trail is cost with no buyer. When the team has not operated one before and the deadline is short, because the operational habits are harder to acquire than the code. And note the cheaper alternative that covers most of the need: current state plus change data capture gives you a history of changes derived from the database's own log, without making every read a fold. Reach for full event sourcing when the events themselves are the domain — ledgers, orders, medical records — rather than when history would merely be useful."
/>

## In production

<RealWorld>

<Claim label="fact" source="ddia">
Deriving views from an immutable event log allows a view to be rebuilt after a bug by reprocessing
the log, which is not possible when state has been updated in place and the previous values
overwritten.
</Claim>

<Claim label="fact" source="ddia">
Immutable data simplifies caching and replication because a value that cannot change cannot become
stale, and it removes the need for invalidation on the copies.
</Claim>

<Claim label="convention" source="martin-fowler">
CQRS is described as separating the model used for updates from the model used for queries, with
explicit warnings that it adds significant complexity and should be applied to the specific parts
of a system that need it rather than universally, and that it is independent of event sourcing.
</Claim>

<Claim label="fact" source="kafka-docs">
Log compaction retains at least the most recent value for each key, which allows a topic to serve
as a durable, replayable record of current state while bounding its growth by the number of keys
rather than the number of events.
</Claim>

<Claim label="fact" source="elasticsearch-docs">
A search index becomes searchable only after a refresh, so a derived index is near-real-time rather
than immediately consistent with its source. That refresh interval is the consistency window of
that read model.
</Claim>

<Claim label="fact" source="clickhouse-docs">
Column-oriented storage reads only the columns a query references, which is what makes
recomputing aggregates over a large event history practical rather than prohibitive.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'Adopting event sourcing and CQRS together as one architecture.',
      why: 'They are independent decisions with independent justifications, and taking both at once is two large complexity increases with no way to tell which one is causing the difficulty you are having.',
      instead:
        'Name the specific problem. If a query is poorly served, add one read model. If history is the domain, store events. Do one, measure, and only then consider the other.',
    },
    {
      mistake: 'Putting personal data in an immutable log.',
      why: 'Erasure obligations and immutability are in direct conflict, and no amount of process resolves it after the fact — the only remedy is rewriting the log, which is exactly what the design forbids.',
      instead:
        'Reference personal data rather than embedding it, or encrypt per subject so a key deletion makes the events unreadable. Decide before the first event is written.',
    },
    {
      mistake: 'Letting a read model accumulate state that exists nowhere else.',
      why: 'A derived view that holds unreconstructible data has quietly become a source of truth, so it can no longer be rebuilt — and rebuildability was the entire property that made its denormalisation safe.',
      instead:
        'Test the rebuild regularly. If rebuilding loses information, that information belongs in the write model, and the discovery is a bug rather than an inconvenience.',
    },
  ]}
/>
