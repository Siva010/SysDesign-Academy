## The problem

You add a second application server behind a load balancer. Deployment is smooth. Then the
support tickets start.

Users are being logged out at random. A multi-step form loses everything on the third step.
An uploaded file is &ldquo;not found&rdquo; immediately after a successful upload.

Nothing is broken on either server. Each is working perfectly with the information it has. The
problem is that they have different information, and the load balancer does not know or care.

## Intuition

One server is a shop with one assistant who remembers you. Two servers is a shop with two
assistants who do not talk to each other, and you get a different one each time you walk in.

Anything the first assistant remembered — that you were logged in, what was in your basket,
the file you just handed over — is invisible to the second.

There are only two ways out:

1. **Always send a customer back to the same assistant.** This works, and it means one busy
   assistant stays busy while the other idles, and everything that person knew is lost when
   they go home.
2. **Move the memory out of the assistants and into a shared ledger both can read.** Now
   either assistant can serve anyone. This is what statelessness means.

The second is almost always right, and it comes with a bill: the shared ledger is now a thing
you must scale, protect, and survive the failure of.

## Concretely

<Example title="Where the state actually goes">

Four kinds of per-request state, and where each moves:

| State | Where it lived on one server | Where it goes with many |
|---|---|---|
| Login session | Server memory | A shared store, or a signed token the client carries |
| Shopping basket | Server memory | The database, or a shared cache |
| Uploaded file | Local disk | Object storage |
| In-progress background job | An in-process timer | A queue or a scheduled job table |

Notice that none of these disappear. Each one becomes a dependency: something over the network,
with its own latency, its own failure mode, and its own capacity limit.

This is the honest description of horizontal scaling. You did not remove state. You moved it,
and in doing so you converted a fast local memory access into a network call — which is why
this step often makes a single request *slower* while making the system able to serve far more
of them.

</Example>

## Formal explanation

A <C id="statelessness">stateless</C> service holds nothing between requests that a subsequent
request needs. Any instance can serve any request, which is what makes instances
interchangeable — and interchangeability is what makes all of the following possible:

- **Horizontal scaling.** Add instances to add capacity.
- **Failure tolerance.** Remove a broken instance and nothing is lost.
- **Rolling deploys.** Replace instances one at a time.
- **Autoscaling.** Instances can appear and disappear on demand.

The <C id="load-balancer" /> distributes requests and stops sending traffic to instances that
fail their <C id="health-check" />. Two kinds are worth distinguishing:

- **L4** balances connections. It is fast and cheap and knows nothing about what is inside
  them.
- **L7** understands requests, so it can route by path, retry idempotent requests on another
  instance, and terminate TLS. It costs more and sees your traffic.

<Callout kind="warn" title="Health checks are load-bearing, and easy to get wrong">
A health check that verifies every dependency will mark every instance unhealthy the moment
one shared dependency degrades. The balancer then has nowhere to send traffic, and a partial
degradation becomes a total outage. A health check should answer "can this instance serve
traffic?", not "is the entire system in perfect condition?"
</Callout>

<Deeper title="Two health checks, not one">

The confusion resolves once you separate two questions that people try to answer with one
endpoint.

**Liveness: is this process broken and in need of restarting?** Should check only local state:
is the event loop responsive, is memory catastrophic, are internal invariants intact. It must
never check a downstream dependency, because restarting your process does not fix somebody
else's database.

**Readiness: should this instance receive traffic right now?** May check whether the instance
has warmed up, established its connection pools, and loaded configuration. It may check
critical dependencies, but only if losing them genuinely makes this instance useless *and*
other instances might be fine.

The failure mode to avoid: a deep readiness check on a shared dependency. When that dependency
degrades, every instance reports not-ready simultaneously, the balancer removes all of them,
and traffic that would have been partially served is now entirely rejected. The correlated
failure is worse than the original one.

</Deeper>

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Hidden local state',
      symptom:
        'Intermittent, user-specific bugs that cannot be reproduced and that resolve on retry.',
      cause:
        'Something still lives in one instance: an in-memory cache, a local file, a scheduled timer, a rate-limit counter.',
      mitigation:
        'Audit deliberately. In-memory caches, local file writes, and in-process schedulers are the usual three, and all three are easy to introduce accidentally.',
    },
    {
      what: 'Deep health checks causing correlated removal',
      symptom:
        'A dependency degrades slightly, and moments later every instance is out of the load balancer pool. Total outage from a partial problem.',
      cause:
        'The readiness check verifies a shared dependency, so all instances fail it at the same instant.',
      mitigation:
        'Separate liveness from readiness. Keep shared dependencies out of health checks unless the instance is genuinely useless without them, and even then consider degrading rather than withdrawing.',
    },
    {
      what: 'Connection multiplication at the database',
      symptom:
        'The database refuses connections during a deploy or a scale-up, although query load is unchanged.',
      cause:
        'Connections scale with instance count times pool size, and a rolling deploy briefly doubles the instance count.',
      mitigation:
        'Use a connection pooler in front of the database, size per-instance pools with the fleet size in mind, and account for the overlap window during deploys.',
    },
    {
      what: 'Retry on a non-idempotent request',
      symptom: 'Duplicate records that correlate with instance failures or deploys.',
      cause:
        'An L7 balancer retried a request on another instance after the first went quiet, and the operation was not safe to repeat.',
      mitigation:
        'Only enable automatic retry for idempotent methods, and make mutations idempotent with a caller-supplied key.',
    },

## Trade-offs

<TradeOff
  decision="Move session state to a shared store rather than using sticky sessions"
  options={[
    'Sticky sessions: pin each user to one instance',
    'Shared session store: any instance can serve any user',
    'Signed tokens: the client carries its own session, no server lookup',
  ]}
  why="Interchangeable instances are the property that makes everything else work: scaling, rolling deploys, instance failure, autoscaling. Stickiness preserves local state by giving up exactly that property."
  gain="Any instance serves any request. Losing an instance loses no sessions. Deploys and autoscaling become routine rather than disruptive. Load spreads evenly."
  sacrifice="A network round trip on every request that needs session data, and a new shared dependency whose availability is now your availability."
  failureModes={[
    'The session store becomes a single point of failure for authentication across the whole system',
    'Its latency is added to every request',
    'It needs its own scaling story, and a hot key if one session is unusually busy',
  ]}
  operationalBurden="Moderate: another system to run, monitor and secure. Usually a managed cache, which reduces the burden but adds a vendor dependency on the login path."
  cost="A cache tier sized for concurrent sessions rather than total users, which is usually small. The real cost is the latency added to every authenticated request."
  whenNot="When the state is genuinely large per user and cheap to rebuild, keeping it local with stickiness can be reasonable — a long-lived WebSocket connection is inherently sticky and there is no point pretending otherwise. Signed tokens are better when you need to avoid the lookup entirely, at the cost of not being able to revoke promptly."
/>

## In production

<RealWorld>

<Claim label="convention" source="sre-book">
Separating liveness from readiness, and keeping shared dependencies out of the checks that
control traffic routing, is standard practice. The failure mode it prevents — correlated
removal of every instance in response to one degraded dependency — turns a partial problem
into a total one.
</Claim>

<Claim label="recommendation" source="aws-builders-library">
Prefer degrading over withdrawing. An instance that can serve 80% of requests correctly is
more useful in the pool than out of it. Health checks that remove capacity during overload
make overload worse, because the remaining instances receive the same traffic spread over
fewer machines.
</Claim>

<Claim label="fact" source="ddia">
Moving state out of application servers converts a local memory access into a network request,
with the corresponding latency, failure and consistency implications. This is a trade rather
than an improvement, and it is the trade that makes horizontal scaling possible.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'We made the service stateless, so we have no state to worry about.',
      why: 'The state moved to a store that is now on the critical path for every request. Its availability is your availability, and its latency is added to yours.',
      instead:
        'Name where each piece went and what happens when that dependency fails. "Sessions in Redis; if Redis is down, existing signed tokens keep working for 15 minutes and new logins fail" is an answer. "It is stateless" is not.',
    },
    {
      mistake: 'The health check verifies the database so we do not send traffic to broken instances.',
      why: 'The database is shared. When it degrades, every instance fails the check simultaneously and the balancer has nowhere to route. You have converted a degraded database into a total outage.',
      instead:
        'Check only what is local and specific to the instance. If a dependency is down, serve what you can and let the error rate speak for itself.',
    },
    {
      mistake: 'Adding more instances will fix the latency.',
      why: 'If the bottleneck is downstream, more instances send more concurrent load to the thing that is already the constraint, which makes it worse.',
      instead:
        'Find the bottleneck first. Horizontal scaling works when the instances are the constraint, and backfires when they are not.',
    },
  ]}
