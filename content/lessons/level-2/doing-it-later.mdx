## The problem

Signing up takes 4 seconds. The handler does seven things: create the user, hash the password,
write an audit record, send a welcome email, generate a thumbnail, notify the analytics
pipeline, and sync to the CRM.

Only the first two need to happen before you can tell the user they are signed up. The other
five are the reason they are waiting — and each one is a third party whose outage becomes your
outage, whose slowness becomes your latency, and whose failure loses a signup that had already
effectively happened.

## Intuition

There are two ways to ask someone to do something.

**Synchronously:** you stand there until it is done. You know the outcome immediately. You are
also blocked, and if they are slow, you are slow; if they are unavailable, you fail.

**Asynchronously:** you leave a note in their inbox and carry on. You are fast and unblocked.
You do not know when it will be done, or whether it succeeded, and you must be able to cope
with the answer arriving later — or not at all.

A queue is the inbox. It buys you three things:

- **Latency**, because the caller stops waiting.
- **Availability**, because the consumer being down no longer fails the request.
- **Burst absorption**, because the queue holds work that arrived faster than it can be
  processed.

And it charges you in a single currency: **you no longer know that the work happened.**
Everything else — retries, duplicates, ordering, dead letters, monitoring lag — is the bill for
that.

## Concretely

<Example title="Which of the seven steps can move">

Ask one question of each step: **if this fails, should the user be told their signup failed?**

| Step | Must be synchronous? | Why |
|---|---|---|
| Create the user record | Yes | It is the operation. Without it nothing happened. |
| Hash the password | Yes | Part of creating the user. |
| Write an audit record | Yes, in the same transaction | Its value is that it cannot diverge from the thing it audits. |
| Send a welcome email | No | Late is fine. Failure is recoverable by retry. |
| Generate a thumbnail | No | The interface can show a placeholder. |
| Notify analytics | No | Nobody's experience depends on it. |
| Sync to the CRM | No | An external system with its own availability, which should never be able to fail a signup. |

Four steps move off the request path. Latency drops from 4 seconds to perhaps 200 ms, and the
signup no longer depends on the availability of an email provider or a CRM.

What you have taken on: those four things must now happen *eventually*, you must be able to
tell when they do not, and each of them may run more than once.

</Example>

## Formal explanation

A <C id="queue" /> decouples producer from consumer in time. The producer writes and returns;
the consumer reads when it is able.

Three properties matter for design.

**A queue absorbs bursts, not sustained overload.** If the arrival rate exceeds the service
rate on average, the queue grows without bound. It does not fix the imbalance; it hides it for
a while, converting an overload problem into a latency problem and then into a storage problem.

**<C id="queue-depth">Depth is a leading indicator</C>.** A growing queue means arrivals exceed
service. It tells you about the problem before users notice, which makes it one of the most
valuable signals in a system — and one of the most commonly unmonitored.

**Delivery is at-least-once in practice.** A consumer that crashes after acting but before
acknowledging will see the message again. This is not a defect in any particular broker; it is
what happens when you cannot make acknowledgement and side effect atomic. The consequence is
that consumers must be idempotent, which is a design constraint rather than an optimisation.

<Callout kind="warn" title="The dual-write problem, arriving early">
If the handler writes to the database and then publishes to the queue, a crash between them
leaves the two permanently disagreeing: a user exists with no welcome email queued, and nothing
knows. This is the dual-write problem, and the standard answer is the transactional outbox —
write the message into the same database in the same transaction, and publish from there.
</Callout>

<Deeper title="Queue or log? They are different tools">

Two shapes are commonly both called "a queue".

**A task queue** is a work list. A consumer takes a message, does the work, acknowledges, and
the message is gone. Well suited to one producer, one logical consumer, and work that is
disposable once done.

**A durable log** is a retained, ordered, replayable sequence. Consumers track their own
position, so several independent consumer groups can read the same messages, and any of them
can rewind.

The distinction matters because the log's extra properties — retention, replay, multiple
independent consumers — are exactly what you need to rebuild a derived store or add a new
consumer after the fact, and are exactly what you are paying operational cost for if you never
use them.

<Claim label="fact" source="kafka-docs">
In a partitioned log, ordering is guaranteed within a partition and not across partitions.
Parallelism within a consumer group is bounded by the number of partitions.
</Claim>

<Claim label="recommendation">
Choose the log when several independent consumers need the same events, or when you may need
to replay history. Choose the task queue when work is consumed once and forgotten. Choosing
the log "in case we need it later" buys a substantial operational bill against a hypothetical.
</Claim>

</Deeper>

## Failure modes

<WhatBreaks
  items={[
    {
      what: 'Poison message blocks a partition',
      symptom:
        'One partition stops making progress while others are fine. Consumer restarts do not help.',
      cause:
        'A message that always fails is retried forever, and in an ordered partition nothing behind it can proceed.',
      mitigation:
        'Bound retries per message and route failures to a dead-letter queue after a limit. Alert on dead letters; an unmonitored dead-letter queue is a silent data-loss mechanism.',
    },
    {
      what: 'Duplicate processing',
      symptom: 'Two welcome emails. Two charges. Two rows where one was expected.',
      cause:
        'A consumer acted and then crashed before acknowledging, so the message was redelivered.',
      mitigation:
        'Make consumers idempotent, keyed on something stable in the message. This is a requirement, not a refinement — at-least-once is what you have.',
    },
    {
      what: 'Silent backlog',
      symptom:
        'Emails arrive six hours late. Search results are stale. Everything reports healthy.',
      cause:
        'Consumers are running and processing, just slower than arrivals. Nothing errors, so nothing alerts.',
      mitigation:
        'Alert on queue depth and on the age of the oldest unprocessed message. Age is the better signal because it maps directly to user-visible staleness.',
    },
    {
      what: 'Dual write between database and queue',
      symptom:
        'Occasional records with no corresponding downstream effect, or events referring to records that do not exist.',
      cause:
        'Two writes to two systems with no atomicity between them, and a crash in the gap.',
      mitigation:
        'Transactional outbox: write the event into the same database in the same transaction, and publish from the outbox asynchronously.',
    },
  ]}

## Trade-offs

<TradeOff
  decision="Move non-essential work off the request path into a queue"
  options={[
    'Keep everything synchronous',
    'Fire-and-forget in a background thread within the same process',
    'Durable queue with workers',
  ]}
  why="Work whose failure should not fail the user's request does not belong on the request path. Anything else means a third party's availability becomes yours, and their latency becomes your latency."
  gain="Request latency drops to the essential work only. The request no longer depends on the availability of anything deferred. Bursts are absorbed rather than rejected, and the deferred work can be retried without the user present."
  sacrifice="You lose the immediate answer. The work becomes eventually consistent, may run more than once, and needs its own monitoring — which is a second system that can be unhealthy while the first looks fine."
  failureModes={[
    'Silent backlog: everything healthy, everything late',
    'Duplicate side effects from redelivery',
    'Poison messages blocking progress',
    'Dual write leaving the database and the queue disagreeing',
  ]}
  operationalBurden="Moderate and frequently underestimated. A broker to run, consumers to deploy and scale, dead letters to triage, and depth and age to alert on. The consumers are a second production service with the same needs as the first."
  cost="Broker infrastructure, worker capacity, and retained messages. Modest in money; the real cost is the operational attention the second path requires."
  whenNot="A background thread in the same process is fine when losing the work on a crash is genuinely acceptable — a metrics ping, a cache warm. It is not fine for anything a user would notice missing, because a deploy will lose it. And do not defer work whose result the caller needs: an asynchronous operation the client immediately polls for is a synchronous operation with extra steps and worse latency."
/>

## In production

<RealWorld>

<Claim label="convention" source="aws-builders-library">
Queue depth and the age of the oldest message are standard operational signals, and message
age maps more directly to user-visible impact than depth does. A queue with 10,000 messages
that drains in 30 seconds is healthy; one with 200 messages whose oldest is four hours old is
not.
</Claim>

<Claim label="fact" source="kafka-docs">
Consumers commit offsets to record progress. The choice of when to commit — before or after
processing — determines whether a crash produces duplicate processing or lost messages. There
is no configuration that avoids choosing.
</Claim>

<Claim label="recommendation" source="ddia">
Design consumers to be idempotent from the start. Retrofitting idempotency after a duplicate
incident is significantly harder than building it in, because by then the side effects are
spread across code that assumed it would run once.
</Claim>

</RealWorld>

## Common mistakes

<Mistakes
  items={[
    {
      mistake: 'We will use a queue to handle traffic spikes.',
      why: 'A queue absorbs a burst. It cannot absorb an arrival rate that exceeds your service rate on average — it just hides the imbalance while depth grows, and every message that eventually completes may already be irrelevant.',
      instead:
        'Say whether the excess is a burst or sustained. Queue for bursts; shed load for sustained overload. Both, if the answer is "sometimes each".',
    },
    {
      mistake: 'The queue guarantees delivery, so the work will happen.',
      why: 'It guarantees the message is retained until acknowledged. It does not guarantee the consumer can process it, that the downstream service is available, or that a permanently failing message will ever succeed.',
      instead:
        'Say what happens after N failures, where those messages go, and who looks at them. An unmonitored dead-letter queue is a place where work goes to be forgotten.',
    },
    {
      mistake: 'We publish the event after committing the transaction.',
      why: 'A crash between the commit and the publish loses the event permanently, with no record that it was ever owed. It is rare, and it is silent, which is the worst combination.',
      instead:
        'Use a transactional outbox so the event and the state change commit together, and publish from the outbox.',
    },
  ]}
