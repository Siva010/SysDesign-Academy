## Problem

A normalised model is excellent for writes: each fact lives in one place, so invariants are easy
to enforce and updates cannot contradict each other.

The same model is often poor for reads. Answering &ldquo;show me this customer's order history
with product names, shipping status and current price&rdquo; means joining six tables, and the
query gets slower as each of them grows.

Optimising the model for reads — denormalising, duplicating — makes writes harder and invariants
easier to violate. The two goals genuinely conflict, and tuning cannot resolve a conflict of
shape.

## Pattern

Stop using one model for both.

- **The write model** stays normalised and enforces invariants. It is the source of truth.
- **One or more read models** are shaped for specific queries: denormalised, pre-joined,
  pre-aggregated.
- Read models are **derived** from the write model, asynchronously — through an event stream, a
  transactional outbox, or change data capture.

Each read model can use a different technology: a search index for text, a columnar store for
analytics, a key-value store for a precomputed feed.

**Read models are eventually consistent with the write model, by construction.** That is the
central cost, and it must be acceptable to the product before you start.

<Callout kind="info" title="CQRS does not require event sourcing">
The two are frequently discussed together and are independent. CQRS separates read models from
the write model. Event sourcing stores changes rather than current state. You can do either
alone, and adopting both at once is a large increase in complexity that should be two separate
decisions.
</Callout>

## Advantages

- **Each side is optimised for its job.** Writes keep invariants; reads are fast and shaped for
  the question.
- **Read and write scale independently.** A read-heavy system can add read models without touching
  the write path.
- **Technology per query.** Search, analytics and key-value lookups each get an appropriate store.
- **Read models are disposable.** Because they are derived, a broken one can be rebuilt from the
  source of truth rather than repaired.

## Costs

- **Eventual consistency**, visible to users. A write followed immediately by a read of a derived
  model may not reflect it.
- **A synchronisation pipeline** to build, monitor and operate, with its own lag and failure modes.
- **More stores to run.** Each read model is a system with backups, upgrades and capacity.
- **Rebuild procedures are mandatory** and must be tested, because read models will drift.
- **Debugging is harder.** &ldquo;Which model is wrong?&rdquo; becomes a routine question.

## When to use it

- Read and write workloads have genuinely different shapes, and one model cannot serve both.
- The read/write ratio is high enough that optimising reads is worth real complexity.
- Eventual consistency on the affected queries is acceptable to the product.
- A specific query is measurably poorly served by the write model — not hypothetically.

## When NOT to use it

- **When one model serves both adequately.** This is most systems. A well-indexed relational
  database answers a wide range of queries, and adding a derived model buys staleness, a pipeline
  and a second store for no benefit.
- **When the query must reflect the latest write.** A balance check, a permission check, or
  inventory at the point of sale must read the authority.
- **As a whole-system architecture.** CQRS is best applied per query, to the specific reads that
  need it. Applying it globally means every read is eventually consistent, including those that
  should not be.
- **Together with event sourcing, adopted at the same time, without a driver for either.** Two
  large increases in complexity taken simultaneously is how teams end up with a system nobody can
  operate or explain.

## Example systems

<Claim label="convention" source="martin-fowler">
CQRS is described as separating the model used for updates from the model used for queries, with
explicit warnings that it adds significant complexity and should be applied to specific parts of
a system rather than universally.
</Claim>

<Claim label="convention" source="ddia">
Deriving specialised views from an authoritative store, asynchronously, is a standard approach to
giving several access patterns their own optimised representation without compromising the source
of truth.
</Claim>

<Claim label="fact" source="elasticsearch-docs">
Search indexes are near-real-time rather than immediately consistent: documents become searchable
after a refresh interval, which is a configurable trade between indexing throughput and freshness.
A search index is a read model, and this is its consistency window.
</Claim>
