## Problem

The old system works, has users, and is wrong in some specific way: the wrong data model, the
wrong technology, or simply unmaintainable.

The tempting answer is a rewrite. It fails predictably, and the mechanism is not about engineering
skill:

- **The old system keeps changing** while you build the new one, so the target recedes.
- **Its mess encodes knowledge** — years of edge cases nobody wrote down.
- **Nothing ships until the end**, so there is no feedback and no evidence.
- **The switch-over is one enormous event**, attempted under maximum schedule pressure with the
  least-tested code path in the project.

## Pattern

Put a facade in front of the old system that can route each request to either implementation.
Then move one capability at a time.

1. Insert the facade. Route everything to the old system. Verify this changes nothing.
2. Implement one capability in the new system.
3. Route that capability to the new system, for a small percentage, then more.
4. Repeat until the old system receives no traffic.
5. Delete it.

The name comes from a fig that grows around a host tree and eventually replaces it, while the
tree is standing throughout.

Every step is small, reversible by a routing change, and ships value. A project cancelled halfway
leaves a working system with several capabilities improved — which a cancelled rewrite does not.

## Advantages

- **Value ships continuously** rather than at the end.
- **Risk is bounded per step.** A problem affects one capability at one traffic percentage.
- **Rollback is a routing change**, not a deploy or a restore.
- **The old system is the specification.** Running both and comparing outputs extracts the
  undocumented behaviour that a rewrite would lose.
- **Cancellation is survivable**, which matters because long projects are frequently cancelled.

## Costs

- **Both systems run simultaneously**, costing infrastructure and cognitive load.
- **The facade is a new component** with its own failure modes, and it sits on the critical path.
- **Data must be shared or synchronised**, which is usually the hardest part and is not solved by
  the routing facade.
- **Calendar time is longer**, even though value arrives sooner.

## When to use it

- The system is live and cannot stop.
- It is large enough that a rewrite would take longer than the old system takes to change
  meaningfully.
- Its behaviour is not fully documented, so the running system is the best specification available.
- There is a request boundary where a facade can sit.

## When NOT to use it

- **When the system is small enough to replace faster than it changes.** A single service with one
  team and a week of work does not need a facade, and the ceremony would cost more than the risk
  it removes.
- **When there is no request boundary.** A library, or logic embedded throughout an application,
  has nowhere for a facade to sit. There, expand-and-contract at the code level is the analogous
  technique.
- **When the two systems cannot share or synchronise data.** The routing facade solves request
  routing; if the data problem is unsolvable, the migration is blocked regardless.
- **When the old system genuinely must be switched off by a date** — a licence expiry, a data
  centre closure. Then the incremental approach may not finish in time, and the honest plan is
  different: a window, with the risk stated.
