## Problem

A user posts. Everyone who follows them should see it in their feed.

The obvious approach is to assemble each feed when it is requested: find who this user follows,
fetch recent posts from each, merge, sort, return. This is **fanout on read**, and it is correct
and simple.

It is also a scatter-gather across many partitions on every feed view. With 500 followees, one
feed request becomes 500 lookups, and the response waits for the slowest of them. Feeds are
viewed far more often than posts are written, so the expensive operation is happening on the
common path.

## Pattern

Do the work once, at write time.

When a user posts, write a reference into each follower's precomputed feed. A feed view then
becomes a single sequential read of a prepared list.

You have moved the cost from the frequent operation to the infrequent one, and turned a
scatter-gather into a lookup.

The write is normally asynchronous: the post is stored synchronously, and a queue drives the
distribution. The author sees their post immediately; followers see it within seconds.

## Advantages

- **Feed reads become trivial**: one sequential read of a prepared list, with latency independent
  of how many accounts the user follows.
- **Read latency is predictable**, because it no longer depends on the slowest of many
  partitions.
- **Read capacity scales cheaply**, since the expensive work happens once rather than per view.

## Costs

- **Write amplification.** One post becomes N writes, where N is the follower count. For an
  account with 50 million followers, that is 50 million writes for one action.
- **Wasted work.** You write into the feeds of inactive users who will never read them.
- **Storage multiplies.** The same post reference is stored once per follower.
- **Deletion and edits fan out too.** Removing a post means removing it from every feed it was
  copied into.
- **Follower changes are complicated.** A new follow either backfills history or starts from now,
  and both need a decision.

## When to use it

- Reads greatly outnumber writes for the same content.
- Follower or subscriber counts are bounded and reasonably uniform.
- Read latency matters more than write latency, which is usually true for feeds.
- A few seconds of delay before content appears is acceptable.

## When NOT to use it

- **When the distribution is heavy-tailed.** A small number of accounts with enormous follower
  counts will dominate total write load. The answer is a hybrid, not a pure strategy — which is
  why every large feed system in public writing describes one.
- **When feeds are read rarely relative to writes.** Precomputing feeds nobody opens is pure
  waste. A notification digest read once a week is better assembled on demand.
- **When the feed is highly personalised or ranked at request time.** If ranking depends on
  signals known only at read time — recency, current context, a model score — the precomputed
  list is only a candidate set, and you still pay read-time work.
- **When content is frequently edited or deleted.** Every mutation fans out too, and the
  amplification applies to corrections as much as to creations.

## Example systems

<Claim label="convention" source="meta-eng">
Public engineering writing about large social platforms consistently describes hybrid
approaches rather than a single fanout strategy, because follower distributions are heavy-tailed
and neither pure strategy handles both ends of the distribution.
</Claim>

<Claim label="convention" source="ddia">
The trade-off between fanout on write and fanout on read is presented as a canonical example of
moving work between the write path and the read path, with the correct choice depending on the
read/write ratio and on the distribution of follower counts.
</Claim>

<Claim label="speculation">
Specific thresholds — the follower count above which an account is excluded from fanout — are
implementation details that depend on the workload. Any particular number quoted for a real
system should be treated as unverified unless it is published by that system's engineers.
</Claim>
