## Problem

You have one production environment. Everything in it is shared: one database cluster, one cache
tier, one deployment, one configuration store.

That means every failure is global by default:

- A bad deploy reaches every user simultaneously.
- A poisoned cache entry is served to everyone.
- One abusive tenant degrades service for all tenants.
- A corrupt configuration change takes down the product.

Geographic redundancy does not help with any of these, because they all propagate through
systems that span regions: the deploy pipeline, the configuration store, the shared data tier.

The problem is not where the infrastructure sits. It is that **there is one of everything.**

## Pattern

Divide the fleet into independent **cells**. Each cell is a complete, self-sufficient stack —
its own compute, its own data store, its own cache — serving a defined subset of users.

- Users are assigned to a cell and stay there.
- Cells do not talk to each other on the request path.
- Deploys go to one cell at a time, with a bake period between.
- A failure — of any kind — affects one cell.

The result is that blast radius becomes a number you choose. With ten cells, a catastrophic cell
failure affects 10% of users rather than 100%.

**Shuffle sharding** is the refinement worth knowing. Instead of assigning each tenant to one
cell, assign each to a random *subset* of cells. With enough cells, no two tenants share exactly
the same subset, so one abusive tenant degrades only the fraction of others who overlap with
them — and complete overlap becomes vanishingly unlikely.

## Advantages

- **Blast radius becomes a design parameter.** Ten cells means a cell-wide failure affects 10% of
  users. You choose the number.
- **Deploys are naturally progressive.** One cell, bake, next cell. A bad release is caught while
  it affects a small population.
- **Noisy neighbours are contained.** One tenant's load stays inside their cell.
- **Cells are a known-good unit.** Capacity planning, load testing and scaling all happen against
  one cell, and growth means more cells rather than a larger and less predictable system.
- **Testing in production becomes reasonable**, because there is a small population to test on.

## Costs

- **Cross-cell operations become hard.** Anything requiring data from several cells — global
  search, cross-tenant analytics, aggregate reporting — needs a separate path.
- **More infrastructure units to operate.** Ten cells is ten databases to upgrade, monitor and
  back up. Without strong automation this is untenable.
- **Cell placement becomes a decision.** Moving a tenant between cells is a data migration.
- **Utilisation falls.** Each cell needs its own headroom, so capacity cannot be pooled across
  cells the way it can in a shared fleet.
- **The router is a new shared component**, and if it fails, all cells become unreachable.

## When to use it

- Multi-tenant, with tenants that can be assigned to a fixed home.
- Blast radius is a real concern: an outage affecting all users is materially worse than one
  affecting 10%.
- Cross-tenant operations are rare, or can be served by a separate derived store.
- Automation is mature enough that operating N stacks costs little more than operating one.

## When NOT to use it

- **When users must interact across the boundary.** A social product where any user can message
  any other has no natural cell boundary, and forcing one produces cross-cell traffic on the
  common path — which is exactly what the pattern is supposed to prevent.
- **When automation is not there yet.** Ten cells with manual operations is ten times the toil,
  and the drift between them will produce failures the single environment did not have.
- **When the system is small.** Cells add fixed cost per cell. Below a certain scale, the cost of
  running several stacks exceeds the value of the isolation.
- **As a substitute for progressive deployment.** If the only goal is limiting deploy blast
  radius, canary releases achieve most of that at a fraction of the cost. Cells are worth it when
  you also want data, cache and tenant isolation.
