# 12. Research Rules for the System-Design Academy

When using this resource library:

### Rule 1 — Do not blindly scrape everything

Build a **source map** first.

Map each resource to:

- topic
- concept
- prerequisite
- depth
- source quality
- production relevance
- interview relevance

Then retrieve material selectively.

---

### Rule 2 — Do not duplicate explanations unnecessarily

When five resources explain caching, synthesize them.

Do not publish five versions of:

> “A cache stores frequently accessed data.”

Instead combine:

- beginner intuition
- formal explanation
- implementation details
- performance implications
- consistency implications
- failure modes
- production lessons

---

### Rule 3 — Primary sources establish truth

Use primary sources to verify:

- protocol behavior
- guarantees
- consistency models
- database semantics
- performance characteristics
- company-specific architecture claims

---

### Rule 4 — Separate fact from inference

Clearly distinguish:

**Documented fact**

**Industry convention**

**Engineering recommendation**

**Simplification**

**Inference**

**Speculation**

Never present speculation about a company's internal architecture as fact.

---

### Rule 5 — Teach through problems

Prefer:

> Problem → Naive solution → Bottleneck → New requirement → Better architecture → New trade-off → Failure mode

over:

> Definition → Definition → Definition

---

### Rule 6 — Every major concept should connect to real systems

For example:

**Idempotency**
→ HTTP APIs
→ payment systems
→ retries
→ duplicate requests
→ distributed workflows
→ message processing

---

### Rule 7 — Always ask what breaks

For every architecture:

- What happens when the database fails?
- What happens when the cache fails?
- What happens when a dependency becomes slow?
- What happens during a network partition?
- What happens when traffic increases 100x?
- What happens when requests are duplicated?
- What happens when one partition becomes hot?
- What happens when a region disappears?

---

### Rule 8 — Do not cargo-cult technologies

Never teach:

> “Use Kafka.”

Teach:

> What problem does Kafka solve, what alternatives exist, what constraints justify it, what operational burden does it introduce, and when is it unnecessary?

Apply the same rule to:

- Kafka
- Redis
- Kubernetes
- microservices
- NoSQL
- GraphQL
- event sourcing
- sharding
- multi-region systems

---

# 13. Target Outcome

The final learner should not merely memorize architectures.

They should be able to receive an unfamiliar problem and reason:

> I understand the primitives, constraints, bottlenecks, scaling mechanisms, consistency requirements, failure modes, and trade-offs well enough to derive a design.

That is the target competency.
